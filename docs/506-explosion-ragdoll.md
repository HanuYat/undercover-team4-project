## 1. 한눈에

지금 폭발 넉백은 **선 자세를 유지한 채 포물선으로 미끄러진다**. 여기에 래그돌을 넣되, 진입 조건을 "폭발에 맞았다"가 아니라 **"죽었다(`IncapacitationCause.Die`)"** 하나로 잡는다.

```
폭발 → 거리 감쇠 데미지 → HP 0 → Die → 래그돌 진입 → 넉백 임펄스 → 착지·정착 → (본부 이송) → 부활 블렌드 → StandUp
                        └ 살아남으면 → 기존 슬라이드 넉백 (PlayerMovement.AddKnockback) 그대로
```

진입을 Die로 통일하면 폭발만이 아니라 **진압봉 사망·납치 린치 사망도 자동으로 래그돌**이 된다. 폭발이 특별한 것은 임펄스가 붙는다는 점 하나뿐이다.

### 확정된 결정 (2026-08-05)

| # | 결정 | 근거 |
|---|---|---|
| 1 | 래그돌 진입은 **`Die` 전이 하나**. 폭발은 임펄스만 추가 | 사망 경로가 여럿인데 폭발만 특수 처리하면 나머지가 그냥 무너진다 |
| 2 | 폭발 데미지에 **거리 감쇠** 도입 (폭심 즉사 / 가장자리 생존) | 현재 균일 60 데미지로는 풀피(100)가 안 죽어 래그돌을 볼 일이 거의 없다. 감쇠를 넣으면 "가까운 놈은 날아가고 먼 놈은 밀린다"가 자동으로 나온다 |
| 3 | 죽는 본인도 **자기 몸이 보이게** 한다 (Die 동안 3인칭 + OwnBody 레이어 해제) | 오너는 자기 메시가 컬링돼 있어(§2) 지금 구조로는 자기 래그돌을 못 본다. 이 기능 재미의 절반이 거기 있다 |
| 4 | 래그돌은 **표현 계층 전용**. 뼈를 동기화하지 않는다 | #506 본문의 합의. 판정은 서버 트랜스폼이 계속 쥔다 |
| 5 | 이번 범위는 **플레이어만**. NPC 래그돌은 후속 | 검증 표면을 줄인다. 빌더·컴포넌트는 NPC 재사용을 염두에 두고 만든다 |

### 프리팹을 뜯어보고 확인한 것 (설계에 직접 영향)

- **`Player` 루트에 Animator + CharacterController + NavMeshObstacle**이 함께 있고, 본은 `Root/Hips` 아래에 **직접** 붙어 있다. 별도 모델 래퍼 오브젝트가 없다.
- **SkinnedMeshRenderer는 `SM_Gen_Chr_Robot_01`** — `Root`의 자식이 아니라 **형제**다.
- **`PlayerLook.m_ownBodyRoot` = `SM_Gen_Chr_Robot_01`** (본이 아니다). 따라서:
  - `ApplyOwnerView`의 `SetLayerRecursively(OwnBody)`가 **뼈를 덮지 않는다** → #506 본문이 걱정한 "오너만 뼈 레이어가 다르다" 함정은 없다.
  - 대신 **뼈는 Default 레이어**라, 콜라이더를 그냥 붙이면 `PlayerInteractor` 조준 레이·상호작용 판정에 자기 뼈가 걸린다 → 전용 레이어는 여전히 필요하다.
  - 그리고 **오너는 자기 몸을 못 본다**(OwnBody 컬링) → 결정 3의 근거.
- 본 이름 (Synty 리그, 실제 확인):
  ```
  Root/Hips
    Spine_01 → Spine_02 → Spine_03 → { Neck → Head, Clavicle_L/R → Shoulder_L/R → Elbow_L/R → Hand_L/R }
    UpperLeg_L/R → LowerLeg_L/R → Ankle_L/R → Ball_L/R → Toes_L/R
  ```
  팔이 `UpperArm/LowerArm`이 아니라 **`Shoulder_*`/`Elbow_*`** 다. 래그돌 위저드·빌더에서 이름을 그대로 쓰면 안 맞는다.
- `HeldItemAnchor`는 `Hand_R` 아래 → 들고 있던 아이템은 부모를 따라가므로 손에 붙은 채로 함께 날아간다(추가 처리 불필요). 아이템 자체 콜라이더가 Default 레이어면 벽·레이 판정에 걸릴 수 있으니 구현 중 한 번 확인할 것.

## 3. 설계

### 3-1. 순서 보장 문제와 그 해법 — **멱등 진입**

서버(호스트)에서는 순서가 이미 맞다: `ServerExplode`가 `TakeDamage` → `SetState(Exploded)` → `OnResolved` 순으로 돈다.

**문제는 원격 클라이언트다.** 사망 사실은 `PlayerIncapacitation.m_causeSynced` 콜백으로, 폭발 사실은 `BombDevice.m_stateSynced` 콜백으로 온다 — **서로 다른 오브젝트의 NetworkVariable이라 같은 틱에 실려 와도 콜백 순서가 보장되지 않는다.** "이 사람 죽었나?"를 뷰가 물어보면 원격에서는 답이 틀릴 수 있다.

순서를 맞추려 들지 말고 **어느 쪽이 먼저 와도 결과가 같게** 만든다:

```csharp
// 두 번 불려도 안전. 이미 래그돌이면 임펄스만 누적한다.
public void EnterRagdoll(Vector3 impulse)
```

| 진입 경로 | 트리거 | 임펄스 |
|---|---|---|
| ① 사망 | `Cause`가 `Die`로 전이 | `Vector3.zero` (힘없이 무너짐 — 진압봉·린치 사망) |
| ② 폭발 | 서버가 보낸 사망자 목록 RPC | `EvaluateKnockback(위치)` |

②만 먼저 와도 래그돌이 켜지고, ①이 뒤늦게 와도 무동작이다. 반대 순서도 같다.

> **①은 이벤트가 아니라 폴링으로 잡아야 한다.** `OnIncapacitatedChanged`는 bool만 넘기고 **원인만 바뀌면 울리지 않는다** ([PlayerIncapacitation.cs:147](../Assets/Scripts/Player/PlayerIncapacitation.cs)). 납치 린치 사망은 `Abducted`/`Lynched` → `Die` 전이라 bool이 안 바뀌어 **이벤트가 아예 안 온다.** `PlayerAnimationDriver`가 `IsProne`을 Update에서 폴링하는 것과 같은 방식으로 `IsDead`를 폴링할 것. (또는 `PlayerIncapacitation`에 `OnCauseChanged`를 새로 추가 — 폴링 쪽이 기존 관례와 일치한다.)

### 3-2. 넉백 이중 적용 방지

`BombExplosionView`에서 "죽은 사람은 건너뛴다"는 판정은 위 이유로 신뢰할 수 없다. **죽은 사람에게 슬라이드 넉백이 들어가도 무해하게** 만드는 쪽으로 해결한다:

- `PlayerMovement.AddKnockback` — 래그돌 활성 중이면 무시.
- `PlayerRagdoll.EnterRagdoll` — 진입 시 `m_knockbackVelocity`·`m_verticalVelocity`를 0으로 클리어.

이러면 순서와 무관하게 항상 옳다.

### 3-3. `PlayerRagdoll` 상태 기계

모든 피어에서 로컬로 도는 MonoBehaviour. 새 매니저가 아니므로 `App` 파사드와 무관(R1~R8 해당 없음).

| 상태 | 내용 |
|---|---|
| **Animated** | 평시. 전 Rigidbody 키네마틱 |
| **Ragdoll** | `animator.enabled = false`, 전 rb `isKinematic = false`, 임펄스 적용. **캡슐이 골반을 추종**(§3-4) |
| **Settled** | 착지 정착 → 루트 잔차 정렬 → **11개 전부 물리**, 골반만 캡슐 앵커에 컴플라이언트 관절로 매단다(`TrailFromCapsule`) |
| **BlendingToAnimator** | 정착 포즈 → 애니메이터 포즈 보간(≈0.4초) 후 Animated로 |

`Settled`에서 네 방식을 거쳤다. 앞의 셋은 반쪽만 얻었고, **넷째가 현재 구현이다**:

| 방식 | 운반·밧줄 | 몸이 흔들리나 | 결과 |
|---|---|---|---|
| 전부 키네마틱 | ✅ | ❌ 한 자세로 굳는다 | 처음 구현 |
| 전부 물리 | ❌ 캡슐만 끌려가고 몸은 바닥에 남는다 | ✅ | — |
| 골반만 키네마틱 | ✅ | ✅ | **§9-7의 원인이었다** |
| **골반을 관절로 매단다** | ✅ | ✅ | 현재 (§9-7 해결) |

골반만 키네마틱이 왜 틀렸는지가 **§9-7**이다 — 요지는 **키네마틱이 무한 강성**이고 **프레임 클럭에 묶여 있다**는 것. 관절은 유한한 힘이라 지면 접촉이 이기고, 골반도 동적이 되어 11개가 같은 클럭을 쓴다.

공개 API:

```csharp
public void EnterRagdoll(Vector3 impulse);   // 멱등
public void ForceSettle();                   // 운반 시작 등 외부 사유로 즉시 정착
public void ExitToAnimator(bool blend);      // 부활(true) / 라운드 리셋·씬 전환(false)
public bool IsRagdollActive { get; }         // PlayerMovement·PlayerLook·AnimationDriver가 읽는다
internal bool IsCapsuleFollowingBody { get; }  // PlayerMovement가 추종 분기 판정에 쓴다 (§3-4)
internal void TickCapsuleFollow();             // 같은 곳에서 매 프레임 호출 — 오너 전용
```

**임펄스 적용:** 전 rb에 `ForceMode.VelocityChange`로 `EvaluateKnockback` 속도를 **균일하게** 주고(몸 전체가 예측 가능하게 날아간다), 거기에 작은 `AddExplosionForce`를 폭심 기준으로 섞는다(사지가 흩어지고 스핀이 생긴다). 회전은 두 번째 성분이 만든다.

**정착 판정:** 전 rb `linearVelocity`(Unity 6 — `velocity`는 deprecated) 크기 합이 임계 이하인 상태가 0.3초 유지, 또는 진입 후 5초 타임아웃.

### 3-4. 캡슐이 시체를 따라간다 — **이 설계의 중심**

> **이 절은 2026-08-05 재작성됐다.** 원래 설계는 "캡슐은 사망 지점에 두고, 정착 순간 시체 밑으로 한 번 텔레포트"였다. 그 **한 번의 늦은 점프가 이 기능 거의 모든 버그의 뿌리였다** — 근거와 거기까지 밟은 함정은 §9에 있다. 아래가 대체안이다.

**비행 중 오너가 매 프레임 캡슐을 골반 위치로 끌고 간다.** [PlayerMovement.cs](../Assets/Scripts/Player/Movement/PlayerMovement.cs)의 `Update`에서 호송(#279)·운반(#365)과 나란한 **세 번째 추종 모드**로 분기한다 — 몸을 끄는 주체가 남이 아니라 **자기 뼈 물리**라는 점만 다르다.

| | 안 하면 (구 설계) | 하면 |
|---|---|---|
| 정착 시 루트 텔레포트 | **1.15m** (실측) | cm 단위 잔차 |
| 원격이 받는 것 | 늦게 도착하는 1m 점프 | 연속 스트림 |
| 필요한 장치 | 수렴 lerp + 릴리스 유예 + 되붙듦 | 없음 |

**추종은 스윕 우선 + 막힌 잔차만 텔레포트다** (`SweepTo` → 잔차 1cm 초과 시 직접 대입). 어느 한쪽만으로는 안 된다:

- **스윕만으로는 원리적으로 못 따라간다.** 서 있는 1.8m 캡슐과 굴러가는 탄도 시체는 갈 수 있는 곳이 다르다 — 난간 너머·공중·좁은 틈. 지형이 갈리는 순간 캡슐이 뒤처지고 동기화되는 위치가 시체를 대표하지 않는다(실측 시체 38.8m / 캡슐 0.23m, §9-11).
- **항상 텔레포트하면** 갈 수 있는 구간에서도 캡슐이 지형을 무시한다.

> **죽은 동안 "몸"은 뼈다.** 뼈가 지형과 충돌하고 물리에 구속된다. 캡슐은 "이 플레이어가 어디 있나"를 기록하는 **대리값**이므로, 몸이 있는 자리에 놓는 것은 물리를 속이는 것이 아니다 — 뼈의 충돌은 그대로다. 호송(#279)이 CharacterController를 끄고 트랜스폼을 직접 옮기는 것과 같은 범주다(`PlayerMovement.SetControllerEnabled`가 그것 때문에 있다).

- **추종은 3차원이다.** 수평만 맞추면 시체가 공중에 있는 동안 이름표·운반 조준·부활 히트박스(전부 루트에 붙어 있다)가 그만큼 어긋나 "모델만 날아간" 것처럼 보인다.
- **중력은 뼈 물리가 든다** — `SweepTo`가 `MoveWithGravity`와 달리 중력을 적분하지 않고 수직 속도를 지운다. 캡슐 쪽에 쌓아 두면 정착 직후 그 속도가 캡슐을 밀어 바닥을 파고든다(#189).
- **잔차 텔레포트는 컨트롤러를 껐다 켜므로 `IgnoreCollision`이 지워진다** — `SetControllerEnabled`를 거쳐 매번 재적용한다. 프레임마다 도는 경로라 놓치면 §9-1이 바로 재발한다.
- **yaw도 매 프레임 따라간다.** 위치만 고치면 **같은 버그가 회전으로 재현된다** — 정착 때 루트 yaw를 한 번에 돌리면 그 회전이 원격에 늦게 도착하고, 정착 후 뼈는 루트의 자식이라 시체가 루트를 축으로 휙 돈다. `Knockdown_StandUp`이 "루트 전방을 향해 누워 있다"를 전제하므로 부활에도 이 값이 필요하다.

**원격은 뼈를 스트리밍된 루트로 당겨온다** (`TickAlignBonesToRoot`). 오너 캡슐이 골반을 따라오므로 **스트리밍된 루트의 위치가 곧 오너 골반의 위치**다 — 뼈를 따로 동기화하지 않고도 오너의 궤적을 받는다(결정 4를 지킨다). 리그 루트 오프셋으로는 못 고친다: **동적 리지드바디는 부모 트랜스폼을 따르지 않는다.** 그래서 뼈마다 같은 델타를 더해 강체로 평행이동한다 — 포즈·상대속도·관절이 보존되고, 동적 바디의 `position` 대입은 텔레포트라 속도가 유도되지 않는다(키네마틱과 반대 — §9-5).

**당겨오기는 비행 중과 착지 후가 다르다** (§9-15에서 비행 중을 되살렸다 — §9-10의 "비행 중엔 당기지 마라"는 **전제가 바뀌어 폐기됐다**):

| | 축 | 속도 | 왜 |
|---|---|---|---|
| 비행 중 | **3차원** | `m_flightAlignPullSpeed` 12m/s | 공중에는 높이를 정해 줄 지형 접촉이 없다. 오너 골반의 고도(=포물선 정점)를 받아야 원격도 같은 궤적을 그린다 — y를 지우면 원격 시체만 안 뜨는 §9-10 증상이 재현된다 |
| 착지 후 | **수평만** | `m_alignPullSpeed` 1.5m/s | 높이의 주인이 각 피어의 지형 충돌로 넘어간다. 구르는 중 델타는 실측 0.15~0.23m라 이 속도로 충분하다 |

어느 쪽이든 **스냅이 아니라 속도 제한 당겨오기**다 — 상한이 있어야 추종이 지형에 막혀 잔차 텔레포트가 크게 들어올 때 그 점프가 뼈로 전달되지 않는다. 비행 중 델타는 진입 시 0에서 출발해 작게 유지되므로 12m/s 상한이 실제로 걸리는 일은 드물다(병리적 경우의 안전망이다).

**뼈를 옮기는 경로는 전부 충돌을 존중해야 한다.** 뼈 자체의 물리는 레이어 매트릭스(`Ragdoll`×`Default`)와 `ContinuousSpeculative` CCD로 벽을 뚫지 않지만, **`position` 대입은 텔레포트라 그 둘이 관여하지 않는다.** 그래서 뼈를 옮기는 곳을 셋으로 못박고 각각 보장한다:

| 경로 | 보장 |
|---|---|
| 물리 시뮬레이션 (비행·구르기) | 매트릭스 + CCD |
| 당겨오기 — 비행 중·착지 후 (`SnapBonesBy`) | **`ClampByWall` 라인캐스트 가드** — 벽에 막히는 지점까지만 옮긴다 |
| 정착 시 포즈 복원 (`RestoreCapturedWorldPoses`) | 직전에 물리로 점유했던 포즈를 되돌리는 것뿐 — 새 위치로 옮기지 않는다 |

**이 표가 셋으로 닫혀 있는 것이 유일한 벽 통과 보장이다.** §9-15로 당겨오기가 비행 중까지 확장됐지만 같은 `ClampByWall`을 지나므로 보장은 그대로다 — **새 경로를 추가할 때 이 표에 줄을 못 넣겠다면 그 경로가 틀린 것이다.** 거리 클램프(시체가 루트에서 N m 벗어나면 회수)를 한때 안전망으로 뒀다가 지운 이유가 이것이다 — 그게 유일하게 충돌을 무시하는 경로가 됐고, 게다가 상한을 정상 비행 거리보다 작게 잡아 매 폭발마다 발동했다(§9-11).

정착 자격에 **당겨오기 완료**가 들어간다(`IsReadyToSettle`). 정착은 골반을 루트에 용접하므로 당기는 도중에 정착하면 남은 델타가 영구 오프셋으로 굳는다 — 당겨오기 1.5m/s로 실측 1.2m면 0.8초가 걸리는데 정지 판정은 0.3초라, 가드가 없으면 거의 항상 먼저 정착한다. 같은 이유로 **공중에서도 정착하지 않는다**(§9-9).

> ⚠ **#506 본문의 "피어마다 착지점이 다른 것은 의도된 감수" 합의를 이 방식이 불필요하게 만든다.** 없애는 방향이라 개선이지만 부록 B 근거표 항목이므로 이슈에 코멘트를 달 것.

정착 시점에 남는 잔차 정렬은 순서를 지켜야 한다 — 뼈는 루트의 자식이므로 루트를 옮기면 뼈도 딸려 간다:

```
① 전 뼈의 월드 포즈(position + rotation)를 캡처
② 전 rb를 isKinematic = true 로 전환
③ 루트를 hips 밑 지면·yaw로 이동 (cm 단위)        ← 오너(또는 오프라인)만
④ 캡처한 월드 포즈를 뼈에 다시 적용
```

- **③은 오너만 한다.** CharacterController + 오너 권한 NetworkTransform이므로 서버가 남의 캐릭터를 옮겨봤자 되돌아온다 (`BombExplosionView` 주석의 논리와 동일). `controller.enabled = false` → 트랜스폼 대입 → `enabled = true` 순서로.
- **②가 운반을 가능하게 한다.** 정착 후 뼈가 다시 부모를 따라가므로 동료가 시체를 운반(#365)할 때 시체가 같이 따라온다.
- 루트 원점은 캡슐 밑면이 아니다 — `center.y - height/2`(이 프리팹 3cm)만큼 내려놓아야 캡슐이 뜨지 않는다.

### 3-5. 카메라 부수 효과 (미해결)

§3-4가 비행 중 루트를 회전시키므로, **카메라가 루트의 자식인 현재 구조에서는 죽는 본인의 화면이 시체와 함께 돈다.** §3-7의 월드 공간 hips 추종(커밋 ④)이 들어오면 사라진다 — 그때까지 오너 시점은 멀미가 날 수 있다. `m_alignRootYawToBody`를 끄면 회피되지만 정착 시 회전 점프가 돌아오므로, 카메라를 먼저 빼는 것이 순서상 맞다.

### 3-6. 부활 블렌드

```
정착 포즈 캡처(각 뼈 localRotation + hips localPosition)
  → animator.enabled = true
  → Animator.Play(Knockdown_Ground, 0, 0)   // Down은 아직 true
  → LateUpdate에서 t: 0→1 (≈0.4초) Slerp/Lerp
  → 완료 후 Down = false 허용 → Knockdown_StandUp(1.17초) → Locomotion
```

**함정:** `Recover()`가 먼저 오면 `PlayerAnimationDriver`가 즉시 `Down = false`를 써 버려서 블렌드 도중에 StandUp이 시작된다. **블렌드 동안에는 AnimationDriver가 `Down`을 내리지 못하게** 막아야 한다(`IsRagdollActive`를 보고 파라미터 쓰기를 보류). 두 컴포넌트가 같은 Animator를 만지므로 역할 분담을 주석으로 명시할 것 — **AnimationDriver는 파라미터만, PlayerRagdoll은 Animator on/off + 뼈**.

### 3-7. 카메라 (결정 3)

Die 동안만:

- **메시 복원** — `SM_Gen_Chr_Robot_01`을 `OwnBody` → `Default` 레이어로 되돌린다 (`PlayerLook.SetLayerRecursively` 재사용). 부활 블렌드 시작 시 원상 복구.
- **카메라는 머리 뼈에 붙이지 않는다** (멀미). 대신 래그돌 활성 동안 **월드 공간에서 hips를 추종**하는 3인칭 오프셋으로 부드럽게 전환한다. 위치만 스무딩하고, 회전은 hips 회전을 따라가지 않는다(부드럽게 look-at만).
  - 캡슐에 고정하면 안 되는 이유: 캡슐은 폭심에 남아 있고 몸만 날아가므로, 정작 자기 몸이 화면 밖으로 사라진다.
  - **부수 효과 하나가 공짜로 따라온다** — 카메라가 루트의 자식이라 §3-4의 ③ 재정렬에서 원래는 화면이 튀는데, 월드 추종이면 그 튐이 안 보인다.
- 정착 후에도 시체 위 3인칭을 유지하다가, 부활 블렌드 시작 시 1인칭으로 복귀.
- 기존 `m_downCamHeight`/`m_downCamPitch` 경로는 **Die가 아닌 프론**(기절·매달기·납치)용으로 그대로 남긴다.

## 4. 데미지 거리 감쇠 (결정 2) — **구현됨 (커밋 ③)**

`EvaluateKnockback`과 같은 모양으로 `EvaluateDamage(Vector3 targetPosition)`를 둔다 — 넉백처럼 **감쇠식을 장치 한 곳에** 둔다. [BombDevice.cs](../Assets/Scripts/Events/Bomb/BombDevice.cs)

**거리는 3차원으로 잰다.** 넉백이 y를 지우는 것은 밀리는 **방향**이 수평이어야 하기 때문이고 피해에는 방향이 없다. 대상 수집(`SuddenEventUtil.CollectFieldPlayers`)도 3차원 거리를 쓰므로, 여기서 수평 거리를 쓰면 **수집은 됐는데 피해가 0인 대상**이 생긴다.

**적용 수치** (플레이테스트로 재확정할 값):

| 파라미터 | 값 | 결과 |
|---|---|---|
| `m_explosionDamage` | 60 → **150** | 폭심 즉사 |
| `m_damageEdgeFalloff` | **0.2** (신규) | 반경 끝 30 데미지 |
| `m_explosionRadius` | 8 (유지) | — |

이 값이면 **즉사 반경 ≈ 3.3m** 이다: `lerp(1, 0.2, d/8) × 150 ≥ 100` → `d ≤ 3.33`. 8m 반경 중 안쪽 3.3m는 죽고(래그돌), 그 밖은 살아서 밀린다(슬라이드 넉백). 수치를 바꿀 때 이 계산을 다시 할 것 — 일반식은 `반경 × (1 − 최대HP/피해) / (1 − 감쇠비율)`이고 툴팁에도 적어 뒀다.

> ⚠ **프리팹의 직렬화 값이 코드 기본값을 이긴다.** `Bomb.prefab`에 `m_explosionDamage`가 저장돼 있으므로 코드 기본값만 바꾸면 적용되지 않는다 — 프리팹도 함께 고쳤다. (§9-3의 "저장되지 않는 값"과 반대 방향의 같은 함정)

> **밸런스 주의:** GDD 365줄에 *"#524로 중간 완충이 사라져 한 번 쓰러지면 본부까지 왕복 — 폭발 등 기존 데미지 수치를 그대로 둘지 플레이테스트로 정한다"* 는 ⚠ 표기가 이미 있다. 6인 중 여럿이 폭심에 몰려 있으면 한 번에 전멸할 수 있다. 즉사 반경을 좁게 잡은 이유다.

**GDD 갱신 필요:** 6-4(시한폭탄 — "미해체 시 폭발(주변 넉백)"에 사망·래그돌 추가), 7-5(데미지 경로), 365줄의 ⚠ 항목. 368줄에 *"폭탄 등 다른 데미지 경로의 플레이어 피격 규칙은 여기서 다루지 않는다"* 로 비어 있는 자리를 채우는 셈이다.

## 5. 작업 순서 (커밋 분할)

### 커밋 ① 프리팹 래그돌 세팅 + 레이어 — **동작 변화 없음**

- **래그돌 본 11개** (Synty 실제 이름):
  | 역할 | 본 |
  |---|---|
  | 골반 | `Hips` |
  | 중간 척추 | `Spine_02` |
  | 머리 | `Head` |
  | 팔(상완) | `Shoulder_L`, `Shoulder_R` |
  | 팔(전완) | `Elbow_L`, `Elbow_R` |
  | 다리(대퇴) | `UpperLeg_L`, `UpperLeg_R` |
  | 다리(하퇴) | `LowerLeg_L`, `LowerLeg_R` |

  발(`Ankle_*`)까지 넣으면 13개. 발은 있으면 착지가 자연스럽지만 없어도 무방 — 성능 여유를 보고 결정.
- 전 Rigidbody **초기 `isKinematic = true`** → 이 커밋만으로는 게임이 전혀 안 바뀐다.
- **신규 레이어 `Ragdoll`** (빈 슬롯 10번 — 현재 0~9만 사용) + 충돌 매트릭스:
  - 켠다: `Ragdoll` × `Default`(지형)
  - 끈다: `Ragdoll` × `Ragdoll`, × 플레이어 캡슐, × `Interactable`, × 아이템 리지드바디
  - 벽 관통 걱정은 없다 — 지형과 충돌하므로 래그돌은 벽을 넘지 않는다. NPC의 `SweepHitsObstacle` 같은 별도 벽 판정이 필요 없는 것이 오히려 래그돌 쪽의 이점이다.

### 커밋 ② `PlayerRagdoll` — 진입·정착·재정렬

- `PlayerRagdoll` 신규 (`Assets/Scripts/Player/View/`)
- `PlayerMovement.Update`에 래그돌 추종 분기 + `PlayerRagdoll.TickCapsuleFollow` (§3-4)
- `PlayerMovement.AddKnockback`에 래그돌 가드 (§3-2)
- `PlayerAnimationDriver`에 "래그돌 중 파라미터 쓰기 보류" 가드 (§3-6)
- `PlayerHeadLook` — 프론 시 가중치를 0으로 **블렌딩**하는데 감쇠에 시간이 걸린다. 래그돌 진입 순간 하드 0으로.
- `OnNetworkSpawn`에서 이미 `Die`면 래그돌을 건너뛰고 곧장 `Knockdown_Ground` 포즈 (늦게 접속한 클라 — `RefreshAimHitbox`가 스폰 시 한 번 맞추는 것과 같은 계열)

### 커밋 ③ 폭발 연동 — 감쇠 데미지 + 사망자 RPC

- `BombDevice.EvaluateDamage` 신설 + `m_damageEdgeFalloff`, `ServerExplode`에서 사용 (§4)
- `Bomb.prefab`의 `m_explosionDamage` 150 / `m_damageEdgeFalloff` 0.2 — 프리팹 값이 코드 기본값을 이긴다
- `ServerExplode`가 데미지 적용 직후 **죽은 사람 목록**을 모아 ClientRpc로 전파 (`NotifyBlastDeaths`)
  - 폭심·반경·세기는 이미 전 피어가 아니까 **사망자 목록만** 보낸다(`NetworkObjectReference[]`). 임펄스는 각 피어가 기존 `EvaluateKnockback`으로 계산 — "넉백 식은 장치 한 곳" 원칙 유지.
  - 사망 판정은 `CollectFieldPlayers`가 행동 가능한(HP>0) 플레이어만 담는다는 점을 쓴다 — 피해 후 `CurrentHp == 0`이면 이 폭발로 죽은 것이다. 피해 전 HP를 따로 기억할 필요가 없다.
  - **RPC가 필요한 이유는 임펄스 하나뿐이다.** 사망 자체는 `PlayerRagdoll`의 폴링이 잡으므로 진압봉·린치는 RPC 없이 처리된다. "누가 이 폭발로 죽었나"만 서버가 안다 — 각 피어가 스스로 판정하면 반경 경계에 선 사람에서 갈린다.
  - 호스트 중복 발행은 기존 `WrongCutClientRpc` 관례(서버는 로컬 직접 발행 + ClientRpc에서 `if (IsServer) return;`)를 따랐다. 오프라인은 로컬 발행만 타고 RPC를 건너뛴다.

  주입된다.** 부드러운 한계와 겹쳐 양의 되먹임이 된다 — 빨라질수록 더 뒤처지고, 더 뒤처지면 스프링이

## 9. 구현 기록 — 물리에서 밟은 함정

증상은 하나였다: **"자연스럽게 쓰러진 뒤 마지막에 한두 번 발작하듯 튄다."** 원인이 하나가 아니라 겹쳐 있었고, 콘솔 로그로 하나씩 갈라냈다. 아래는 전부 실제로 밟은 것이고, 같은 함정이 NPC 래그돌(§8)에서 되풀이되기 쉬우니 남긴다.

### 9-1. 자기 캡슐과의 충돌 무시가 지워진다 — *쓰러지는 순간 튐*

래그돌은 죽는 순간 **자기 CharacterController 캡슐 안에서** 출발한다. 캡슐이 지형과 같은 `Default` 레이어라 충돌 매트릭스로는 못 가르고, 런타임 `Physics.IgnoreCollision`으로 끈다.

**이 상태는 콜라이더를 껐다 켜면 초기화된다(Unity 사양).** `Awake`에서 한 번 거는 것으로는 부족하다 — `PlayerMovement.SetPose`가 스폰 포즈를 적용할 때 **같은 프레임 안에서** 껐다 켜므로 폴링으로는 전이조차 볼 수 없다. 세 곳에서 다시 건다: 래그돌 진입 직전(결정적 지점) / `TrailFromCapsule`(정착) / 캡슐이 여러 프레임 꺼졌다 켜지는 것이 관측될 때(호송·운반). **뼈 콜라이더를 평소 끄는 최적화를 넣으면 켜는 자리가 네 번째 리셋 지점이 된다** — 그 증상이 하필 "쓰러지는 순간 튐"이라 다른 원인과 구분이 안 되므로, 진단 로그의 `자기캡슐` 표시로 확인할 것.

### 9-2. 관절 `projection`은 켜면 안 된다

늘어난 관절을 매 스텝 강제로 되당기는 기능인데, 두 번 물렸다:

- 좁게(0.02m / 5°) 잡으면 매 스텝 보정이 걸려 몸이 폭주한다
- 느슨하게(0.1m / 180°) 잡아도 **projection은 충돌을 무시하고 위치를 옮기는** 기능이라, 밧줄로 끌 때 관절이 늘어나는 순간 머리를 지형 안으로 밀어 넣는다

위저드 기본값도 꺼짐이다. 대신 solver 반복으로 관절을 붙든다 — 그런데 그게 §9-3 때문에 안 걸려 있었다.

### 9-3. `solverIterations`·`maxDepenetrationVelocity`는 프리팹에 저장되지 않는다

**Rigidbody의 직렬화 필드가 아니다.** `Player.prefab`의 Rigidbody 블록은 `m_CollisionDetection`에서 끝나고 해당 항목이 아예 없다. 에디터 스크립트에서 아무리 써도 저장되지 않고, 인스턴스가 만들어질 때마다 `DynamicsManager.asset`의 프로젝트 기본값으로 되돌아온다.

| | 의도(`PlayerRagdollSetup`) | 실제 프리팹 |
|---|---|---|
| `maxDepenetrationVelocity` | 3 | **10** (기본값) |
| `solverIterations` | 12 | **6** (기본값) |
| `solverVelocityIterations` | 4 | **1** (기본값) |

레이어·`isKinematic`·보간·CCD·관절 `preprocessing`/`projection`은 직렬화되므로 정상 반영됐다 — 그래서 셋업이 돌아간 것처럼 보였다. → **`PlayerRagdoll`이 `Awake`에서 런타임에 건다.** 에디터 스크립트로 되돌리지 말 것.

### 9-4. 정착 텔레포트에 `SetPose`의 짝이 빠져 있었다

`Settle()`은 루트를 시체 밑 지면으로 옮기면서 `PlayerMovement.SetPose`를 거치지 않고 트랜스폼을 직접 만진다. 그래서 `SetPose`가 #189 때문에 하던 두 가지가 빠져 있었다:

- **쌓인 수직 속도를 안 지웠다** → `ClearExternalVelocity()` 추가
- **루트 원점을 지면 점에 그대로 놓았다** → 루트 원점은 캡슐 밑면이 아니다. 캡슐은 `center.y ± height/2` 범위라 밑면이 루트보다 `center.y - height/2`만큼 위에 있고(이 프리팹은 3cm), 그대로 두면 캡슐이 떠서 출발한다. `isGrounded`는 `Move()`를 한 번 돌기 전까지 거짓이라 그동안 중력이 쌓인다

둘 다 캡슐을 밀고, **정착 후 골반은 키네마틱이라 캡슐에 매달려 있으므로** 그 이동이 시체를 통째로 끌어간다.

### 9-5. 원격 피어 — 시체가 아직 이동 중일 때 물리로 놓으면 안 된다

> **이 절의 처방(유예·되붙듦)은 §9-6이 폐기했고 코드에 없다.** 증상 관측과 마지막 단락의 "키네마틱 유도 속도"는 여전히 유효하다(그 짝은 `SetBodyKinematic`에 남아 있다). 왜 처방이 틀렸는지가 §9-6이다 — 되돌리지 말 것.

여기가 가장 오래 걸렸다. 정착 직후 원격의 시체는 두 가지가 동시에 끌어온다:

- **리그 루트** — `TickConverge`가 로컬 착지점과 오너 확정 위치의 차이를 흡수 (실측 **1.18~1.38m** / 0.25초)
- **플레이어 루트** — NetworkTransform이 오너 확정 자리로 이동 (실측 한 스텝 **219mm**)

그 이동 중에 `PinHipsOnly()`를 부르면 **골반만** 키네마틱이라 리그에 용접된 채 1m 넘게 끌려가고, 나머지 뼈는 이미 바닥에 눌러앉아 물리로 버틴다 → 관절 10개가 통째로 늘어났다 되튕긴다. 로그에서 Δv가 사지(`Elbow`·`Shoulder`·`Head`·`LowerLeg`)에만 몰리고 바닥과의 충격이 10을 넘던 것이 이 현상이다.

→ **움직임이 멎은 뒤에 놓아준다** (`BeginPhysicsRelease`/`TickPhysicsRelease`). 유예 동안에는 전 뼈가 키네마틱이라 스켈레톤이 강체로 함께 미끄러진다. 조건은 *수렴 종료 + 루트가 한 프레임 5mm 미만 이동*, 못 만나면 1초 타임아웃(움직이는 것 위에 얹힌 시체도 결국 운반·부활이 되어야 하므로).

그리고 그 유예를 걸고도 릴리스 직후 **접촉 없이 Δv 7.1m/s**(머리)가 남았다. 원인은 따로였다:

> **키네마틱 바디도 트랜스폼이 움직이면 PhysX가 그 이동에서 속도를 유도하고, 그 속도는 `isKinematic = false` 시점에 살아난다.**

수렴이 리그를 1.18m 끌어온 속도(≈4.7m/s, 회전 중심에서 먼 뼈는 더 빠름)를 그대로 물고 물리로 돌아간 것이다. Δv 순서가 머리 7.1 > 어깨·팔꿈치 6.0 > 척추 2.7로 **리그 루트에서 먼 순서 그대로**였던 것이 근거다. → 속도를 **양쪽 전이에서 모두** 지운다: 키네마틱으로 넘기기 *전에*, 물리로 돌려줄 때는 돌려준 *뒤에*(키네마틱 상태에서는 속도 대입이 적용되지 않는다).

### 9-6. 근본 원인은 하나였다 — **늦게 한 번 오는 캡슐 텔레포트**

§9-1~9-5를 하나씩 잡고도 튐이 남았다. 마지막 로그가 범인을 확정했다:

```
[물리 복귀] 유예 0.26s (정지확인), 정지유지 0.26s      ← 전 구간 내내 루트가 정지였다
직후 루트Δ 수평:  94 → 108 → 143 → 86 → 42 → … → 1.8mm   (총 0.74m, 0.44초)
그 첫 스텝의 Δv:  Spine_02 3.38 < Shoulder 6.05/6.80 ≈ Elbow 6.40 < Head 7.19
                 다리는 0.3~0.7 (바닥에 눌려 있어 안 끌림), 접촉 충격은 대부분 0.00
```

Δv가 **골반에서 먼 순서 그대로**이고 접촉이 없다 = 부딪힌 게 아니라 **관절이 끌어당겼다.** 그리고 기다리라고 만든 유예는 **전 구간 잠잠했다** — 기다려야 할 이동이 유예가 끝난 *다음에* 시작됐다.

**"루트가 잠잠하다"는 이동이 끝났을 때만이 아니라 아직 시작도 안 했을 때도 참이고, 둘은 구별할 수 없다.** 정착은 각 피어가 자기 로컬 정지 판정으로 트리거하고 착지점이 1m 넘게 다르므로 **오너가 원격보다 늦게 정착하는 것이 정상**이다. 얼마나 늦을지는 물리 발산이 정하므로 **상한이 없다** — 대기 시간·유지 시간·되붙듦 어느 것도 근본이 아니었다.

→ **점프 자체를 없앴다** (§3-4 캡슐 추종). 그 결과 다음이 전부 삭제됐다 (약 130줄, 노브 5개):

| 삭제 | 있던 이유 |
|---|---|
| `BeginConvergence`/`TickConverge` | 원격이 1.2m 발산을 마지막에 흡수하려고 |
| `ApplyPosesRelativeTo` | 그 흡수의 출발 포즈를 잡으려고 |
| `BeginPhysicsRelease`/`TickPhysicsRelease` | 점프가 끝날 때까지 물리 복귀를 미루려고 |
| `RepinIfRootMovesAgain` | 그 타이밍을 못 맞춰서 사후에 되붙들려고 |
| `m_boneRootRest*` | 수렴 오프셋의 기준점 |

**교훈:** 두 클럭(프레임/네트워크 vs 물리)을 잇는 자리에 "언제 도착하나"를 재는 코드를 쌓지 말 것. 도착 시점을 알아야 하는 구조 자체가 틀렸다는 신호다. §9-7이 같은 교훈의 다른 사례다.

### 9-7. 몸이 찢어지고 허리가 땅에 박힌다 — **해결 (골반 용접 제거)**

증상은 둘이고 **정착만으로도 난다** — 처음에는 밧줄로 끌 때만 보이는 줄 알고 커밋 ④로 미뤄뒀지만, 그게 오판이었다:

- **가만히 있어도 허리가 땅에 박힌 채 몸이 부들부들 떨린다** (운반·밧줄 없이, 정착 직후부터)
- 시체를 밧줄로 끌면 **팔이 잠깐씩 늘어나거나 몸이 살짝 찢어진다**

아래는 밧줄 드래그 중 정착 후(`Settled`) 원격에서 관측한 것:

```
루트Δ 수평:  41.8 → 55.3 → 141.0 → 51.9 → 87.0 → 84.2 → 208.9 → 65.3 mm/step
그 직후 Δv:  Shoulder 2.91 / Elbow 3.93 / UpperLeg 2.71 / LowerLeg 2.57  ← 충격 대부분 0.00
```

**앵커가 한 물리 스텝에 42~209mm로 5배씩 요동친다.** 208.9mm/step = 10.4m/s는 사람이 끄는 속도가 아니라 NetworkTransform 보간 지터다. 직후 Δv가 전 뼈에 퍼지는데 접촉 충격은 0 — 또 **관절이 끌어당긴 것**이다.

원인은 하나, 증상은 둘:

| 증상 | 원인 |
|---|---|
| 팔이 잠깐씩 늘어난다 | 정착 중 골반은 키네마틱으로 루트에 **강체 용접**돼 있고(`PinHipsOnly`) 루트는 프레임(원격은 네트워크 보간) 클럭으로 움직인다. 나머지 10개 뼈는 물리 클럭. 관절이 그 두 클럭을 이으므로 스텝마다의 양자화 차이가 곧 관절 위반이 되고, 솔버가 한 스텝에 해소하며 사지를 채찍처럼 당긴다 |
| 몸이 살짝 찢어진다 | 동적 뼈는 `Interpolate`(한 물리 스텝 과거로 렌더), 키네마틱 골반은 `None`(현재 프레임). 3m/s면 골반 이음새에 상시 **약 6cm** 어긋남 |

**§9-6과 같은 계열이다** — 부모가 솔버와 다른 클럭으로 움직인다. 이번엔 그것이 관절을 통해 새어 나온다.

**해결 (구현됨 — `TrailFromCapsule`):** 골반도 **동적으로** 만들고 캡슐과의 결합을 강체 용접에서 **관절(컴플라이언트)** 로 바꾼다. 동적 리지드바디는 부모 트랜스폼을 따르지 않으므로 골반을 동적으로 만들면 **계층 용접 자체가 사라지고**, 11개 뼈 전부가 같은 클럭·같은 보간 모드가 된다 — 두 증상이 동시에 없어진다. 끄는 힘은 관절이 전달하므로 앵커 지터가 강체 제약 위반이 아니라 작은 힘 리플로 바뀌고, 몸이 흔들리는 것도 유지된다. 계층은 그대로 두므로 **리패어런트 위험이 없다** — 애니메이터 복귀 시 전부 키네마틱으로 돌리면 기존 경로가 그대로 작동한다. 비용은 앵커 오브젝트 + 관절 셋업과 노브 2개(`m_trailSpring` 3000 / `m_trailDamper` 200)였다.

**허리가 박히는 쪽은 근거가 하나 더 있다 — 키네마틱은 무한 강성이다.** 골반이 지면과 안 맞는 높이에 고정되면 거기 관절로 매달린 `Spine_02`가 지면으로 밀려 들어가는데, 물리는 키네마틱 골반을 밀어낼 수 없으므로 매 스텝 같은 싸움을 되풀이한다. 실측:

```
Settled/원격 | 골반키네=True | 루트↔골반=0.34m  ← 수십 스텝 내내 고정
  Spine_02 ← SafetyNetFloor 충격 45.66 → 121.49 → 95.35 → 89.16 → 58.71 …
  Head     ← SafetyNetFloor 충격 38.85 → 88.02 → 87.54 → 65.52 → 73.11 …
  그런데 Δv는 0.2~1.5로 작다
```

**충격이 세 자리인데 Δv가 작고 그게 수십 스텝 지속되면 = 부딪혀 튕긴 게 아니라 계속 눌려 밀려나는 중이다.** 스프링은 유한한 힘이라 지면 접촉(하드 제약)이 항상 이기므로, 골반이 제 높이를 찾아 올라오고 이 싸움 자체가 없어진다.

> **왜 §9-14가 이걸 드러냈나.** 그 전에는 시체가 바닥을 통과해 떨어져서 눌릴 일이 없었다 — 안전망에 걸리게 되자 비로소 보였다. **버그를 고치면 그 뒤에 가려져 있던 버그가 나온다**는 흔한 순서다.

**검증할 것:** 정착 후 `Spine_02`·`Head`의 지속 접촉 충격이 사라졌는지, `골반키네=False`로 찍히는지, 그리고 **시체가 잠드는지**(`m_SleepThreshold` 0.005 — 스프링이 계속 힘을 주면 11개 동적 바디가 영구히 깨어 있을 수 있다. 그게 뼈 콜라이더 평소 비활성화의 실제 근거가 된다).

같은 로그에서 함께 관측된 것 — 드래그 중 `Spine_02 ← 충격 5.79~14.73`이 **지속**된다. 멈춘 몸의 접촉 충격이 두 자리면 척추가 지면에 눌려 계속 밀려나는 중이라는 뜻으로, 키네마틱 골반이 지면과 안 맞는 높이에 몸을 붙들고 있는 것과 같은 원인일 수 있다 — 위 수정으로 함께 사라질 후보다.

### 9-9. 공중에서 정착하면 시체가 허공에 굳는다

커밋 ③으로 임펄스가 처음 붙자 바로 나왔다 — **시체가 날아간 뒤 내려오지 않고 공중에 떠 있다.**

```
진입 — 루트 (15.27, 0.46, 18.76), 골반 (15.31, 1.35, 18.76), 임펄스 (12.73, 13.28, 26.63), 권한 원격
지면 판정 실패 — 골반 높이(8.95)를 쓴다
정착 — 골반 (15.40, 8.95, 18.88) → 루트 (15.38, 0.00, 18.79), 경과 5.01s/타임아웃, 권한 원격
```

`m_settleTimeoutSeconds`(5초)가 **착지 판정 없이 시간만 보고** 공중에서 터졌다. 그러면:

1. `GroundUnder`는 2m만 아래로 쏘니 9m 밑 지면을 못 찾고 골반 높이를 반환한다
2. **원격은 루트를 옮길 권한이 없으므로** 루트는 y=0.00에 남는데, 뼈는 y=8.95의 월드 포즈로 복원된다
3. `PinHipsOnly`가 골반을 루트에 용접 → 골반이 **+8.95m 로컬 오프셋**을 물고 키네마틱 → 영구 부양

`GroundUnder`의 옛 주석 *"못 찾으면 골반 높이를 쓴다 — CharacterController의 중력이 남은 차이를 메운다"* 가 **원격에서 거짓**이었다. 원격은 `PlayerMovement`가 꺼져 있어 중력이 아예 돌지 않고, 정착 후에는 오프셋이 굳는다. 이 주석을 믿고 짠 것이 세 번째 고리였다.

→ **정착 자격에 실제 지면 판정을 넣었다**(`IsReadyToSettle`). 타임아웃이 걸려도 공중이면 기다린다. 맵 밖으로 떨어진 시체가 `Ragdoll`에 갇히지 않게 배수 타임아웃(`k_lostBodyTimeoutFactor`)만 최후 안전장치로 둔다.

> **곁길로 한 번 빠졌다 — 기록해 둔다.** 처음에는 원인을 "임펄스가 과하다"로 보고 넉백 세기에 0.25를 곱했다. 크기 32m/s가 9m를 띄운 건 사실이지만 **부양의 원인은 지면 판정이고 세기는 감(感) 문제**다. 게다가 균일하게 곱하면 상승 비율 0.45가 그대로 남아 수직이 3.3m/s로 죽어 시체가 바닥만 훑는다. 두 사안을 섞지 말 것 — 세기를 조정하고 싶으면 `m_knockbackForce`·`m_knockbackUpwardRatio`를 만진다(살아남은 사람의 슬라이드 넉백과 같은 세기를 쓰는 것이 전제다).

### 9-10. 원격 정렬이 시체의 궤적을 캡슐의 궤적으로 덮었다

§9-9를 고치자 다음이 드러났다 — **오너가 죽으면 잘 날아가는데 클라이언트가 죽으면 위로 안 뜨고 옆으로만 간다.**

임펄스는 정상이었다. 원격 `(-29.06, 13.28, 5.08)`, 수직 13.28로 오너(12.27/12.92/13.14)와 같다. 원격 전용 코드는 `TickAlignBonesToRoot` 하나뿐이고, 그게 이렇게 돼 있었다:

```csharp
Vector3 delta = m_root.position - m_hipsBone.position;
delta.y = 0f;
m_bodies[i].position += delta;      // 전 뼈에 그대로 — 매 프레임
```

이건 "발산을 보정한다"가 아니라 **"골반의 수평 위치를 루트의 수직축에 매 프레임 완전히 못박는다"** 다. 그런데 원격의 루트는 오너의 캡슐이고, 캡슐은 `Move()` 스윕으로 지형을 타는 **접지된 CharacterController**다. 시체는 29m/s 포물체다.

> **포물체와 지면 스위퍼는 매 프레임 크게 갈라지는 것이 정상이다.** 그 차이를 전부 되돌리면 남는 것은 캡슐의 궤적이다.

그래서 원격에서 보이던 "옆으로 날아가는 것"은 시체의 궤적이 아니라 **캡슐의 궤적**이었다. 수직까지 죽은 것은 부작용이다 — 29m/s면 프레임당 0.5m씩 되돌리는 셈이라 뼈가 매 프레임 지형으로 밀려 들어가고, 그 접촉 해소와 관절 풀이가 계통 전체의 에너지를 빼간다.

§3-4에 적었던 *"매 프레임 보정하므로 발산이 누적되지 않는다 — 델타가 계속 작게 유지되는 것이 핵심"* 이 **틀린 주장이었다.** 델타가 작게 유지되는 것은 시체와 캡슐이 비슷하게 움직일 때뿐이다. §9-9의 로그에서 골반이 5초간 수평 9cm만 움직였던 것("설명 안 됨"으로 남겨 뒀던 값)이 이미 이 증거였다.

→ **착지한 뒤에만 당겨오고, 보정 속도에 상한(`m_alignPullSpeed` 1.5m/s)을 둔다.** 판정은 정착 자격과 같은 것을 써서 "정렬은 안 했는데 정착은 된다"가 생기지 않게 했고, 정착 자격에는 반대로 **당겨오기 완료**를 넣었다(§3-4).

> ⚠ **이 절의 "착지한 뒤에만"은 §9-15가 폐기했다.** 상한을 두는 것과 정착 자격 결합은 유효하다. 폐기된 것은 *비행 중엔 당기지 않는다*는 부분뿐이고, 그 이유는 이 절의 근거가 **캡슐이 시체를 못 따라가던 시절의 측정**이었다는 것이다 — 되돌리기 전에 §9-15를 읽을 것.

### 9-11. 비행 거리는 취향이 아니라 설계 제약이다

§9-10을 고쳐 원격도 자기 물리로 날게 하자 다음이 나왔다 — **이름표는 제자리인데 모델이 사라졌다.**

```
진입:  루트 (-27.68, 54.81)  골반 (-27.69, 54.82)  임펄스 (20.01, 12.45, -19.11)
정착:  골반 (-5.77, 22.69)   루트 (-27.57, 54.61)  루트 텔레포트 38.65m, 경과 20.01s/타임아웃
```

두 숫자가 결정적이다:

- **원격 시체는 38.8m 이동했다**
- **오너의 캡슐은 0.23m 움직였다** — `TickCapsuleFollow`가 매 프레임 전체 델타로 `Move()`를 부르는데도

`Move()`는 스윕이므로 **첫 장애물에서 막힌다.** 38m를 프레임당 0.5m씩 쓸어 가면 도시 씬에서 즉시 걸린다. 그 순간 §3-4의 전제가 무너진다:

> "스트리밍된 루트의 수평 위치가 곧 오너 골반의 수평 위치다"

정착은 20.01초(배수 타임아웃)에 걸렸고 — 당겨오기 1.5m/s로 38m는 26초가 걸려 `IsReadyToSettle`이 계속 막았다 — 그 38.65m가 영구 오프셋으로 굳었다.

**그래서 시체는 캡슐이 따라올 수 있는 거리 안에 떨어져야 한다.** 이름표·운반 조준·부활 히트박스가 전부 루트에 붙어 있다. 세기는 취향이 아니라 이 제약을 만족해야 하는 값이다 — §9-9에서 "세기는 감(感) 문제"로 정리했던 것을 여기서 뒤집는다. 부양의 원인이 지면 판정이었던 것은 맞지만, 거리는 별개의 구조적 제약이었다.

> **골반을 동기화해도 이건 고쳐지지 않는다.** 원격이 오너 궤적을 완벽히 재현해도 캡슐은 여전히 38m 뒤에 있다 — 판정 위치가 갈리는 문제는 동기화의 문제가 아니다.

→ 세 가지를 넣었다:

| | 내용 |
|---|---|
| 임펄스 | `m_ragdollImpulseScale` 0.1 / `m_ragdollLiftRatio` 1.8 — 폭심에서 수평 3.0 · 상승 5.4m/s → **정점 약 1.5m, 비행 1.1초, 3~4m** |
| 캡슐 추종 | **스윕 우선 + 막힌 잔차만 텔레포트**(§3-4) — 추종이 지형에 막혀 실패하는 경로 자체를 없앴다 |
| 잔차 텔레포트 로그 | 스윕이 막힌 첫 순간을 찍는다 — 자주 보이면 임펄스가 지형에 비해 과하다는 신호다 |

세기·들어올림을 따로 잡는 이유는 §9-9의 ⚠와 같다. 균일 배율은 상승 비율 0.45를 살려 둬 시체가 바닥을 훑는다.

> **거리 클램프는 넣었다가 지웠다.** "시체가 루트에서 5m 벗어나면 회수"를 안전망으로 뒀는데, ① 상한(5.0m)이 정상 비행 거리(5.05m)보다 작아 **매 폭발마다 발동해 막으려던 순간이동을 스스로 만들었고**(안전망은 봉투 바깥에 둬야 한다), ② 회수가 텔레포트라 **뼈를 옮기는 유일한 무보장 경로**가 됐다(§3-4의 표). 캡슐 추종이 실패하지 않게 된 뒤로는 발동 조건 자체가 사라져 삭제했다.

### 9-12. `[SerializeField]` 기본값은 두 번 배신한다

이 이슈에서 **직렬화 값 때문에 세 번 헤맸다.** 방향이 매번 달라 정리해 둔다.

| | 증상 | 이유 |
|---|---|---|
| §9-3 | 에디터 스크립트로 써도 **저장이 안 된다** (`solverIterations` 등) | Rigidbody의 직렬화 필드가 아니다 → 런타임에 걸어야 한다 |
| §4 | 코드 기본값을 바꿨는데 **적용이 안 된다** (`m_explosionDamage`) | 프리팹에 값이 저장돼 있다 → 프리팹도 고쳐야 한다 |
| 여기 | 코드 기본값을 바꿨는데 적용이 안 되고, **프리팹 파일에는 그 필드가 아예 없다** | 아래 |

`m_maxBodyDistance`를 `5f`로 추가해 한 번 컴파일한 뒤 `15f`로 고쳤더니 런타임은 계속 **5**를 썼다. `Player.prefab`을 열어 봐도 `m_maxBodyDistance` 줄이 없다.

> 필드를 처음 추가해 컴파일한 순간 Unity가 **메모리상의 프리팹 직렬화 데이터에 그때의 기본값을 굽는다.** 이후 코드 기본값을 바꿔도 이미 직렬화된 인스턴스는 되살아나지 않는다. 디스크에 안 써졌으니 **파일을 읽어도 보이지 않는다** — §4보다 나쁘다.

증상은 이렇게 나타났다: 클램프 상한을 15m로 올렸는데 로그가 계속 `(상한 5.0m)`을 찍었다. **로그가 값을 함께 찍고 있었던 것이 유일한 단서였다** — 안 찍었으면 "왜 안 고쳐지지"에서 한참 헤맸을 것이다.

→ **새 노브를 넣을 때는 프리팹에도 명시적으로 박고**, 진단 로그에는 판정에 쓴 값을 함께 찍을 것. `m_alignPullSpeed`를 그렇게 했고, 지워진 `m_convergeSeconds` 줄도 함께 정리했다. (`m_maxBodyDistance`는 그 뒤 §9-11에서 삭제됐다 — 함정을 드러낸 뒤 제 역할을 끝냈다)

### 9-13. 검증 결과 (오너 경로, 2026-08-05)

메인 Editor에서 직접 죽어 **`권한 오너` 로그를 처음으로 확보했다.** 그동안 전부 `원격`이었던 것은 죽은 쪽이 가상 플레이어였기 때문이고, `IsOwner` 문제는 아니었다.

- [x] **정착 텔레포트 1.15m → `0.03m`** — §3-4 캡슐 추종의 단일 판별점. 통과.
  잔차 3cm는 **정확히 `CapsuleBottomOffset`**(캡슐 밑면 보정)이고 수평은 0이다 — 골반 `(-3.85, 47.41)` = 루트 `(-3.85, 47.41)`. 추종이 완전히 붙어 있다는 뜻이다.
- [x] **`캡슐=접지`** (이전엔 내내 `공중`). `수직속도 = -2.17`은 접지 클램프(`k_groundedStickVelocity` −2 + 한 스텝 중력)이므로 **중력이 쌓이지 않는다** — §9-4의 두 번째 함정이 구조적으로 사라졌다.
- [x] 비행 중 `루트Δ 수평`이 실제로 움직인다(173→282→17→29mm, 이전엔 0.0mm). `루트↔골반`이 0.91 → 0.23m로 줄며 캡슐이 시체를 따라잡는다.
- [x] `물리 복귀`·`되붙듦` 로그 없음 — 삭제된 장치이므로 정상.

**다음 세션의 판별점 (커밋 ③ 임펄스 경로 — 아직 안 봄):**

- [ ] **오너·원격 양쪽에서** 시체가 위로 뜨고 3~4m 안에 떨어지는지. §9-10·§9-11이 둘 다 "한쪽만 보면 정상"이었으므로 두 화면을 같이 볼 것
- [ ] **시체가 벽을 뚫지 않는지** — §3-4의 "뼈를 옮기는 경로" 표가 그 보장이다. 뚫린다면 그 셋 중 어디인지부터 가른다
- [ ] `정착 — … 시체 이동 N.NNm, 루트 이동 N.NNm` — **두 값이 비슷해야** 캡슐 추종 성공이다. 시체만 갔으면 루트가 시체를 대표하지 못한다는 뜻
- [ ] `캡슐 잔차 텔레포트` 빈도 — 매번 나오면 임펄스가 지형에 비해 과하다(캡슐이 스윕으로 못 쫓아갈 만큼 멀리 난다) → `m_ragdollImpulseScale`을 낮춘다
- [ ] `거리 클램프`·`물리 복귀`·`되붙듦` 로그가 안 나오는지 — 전부 삭제된 장치다
- [ ] 가장자리 생존 (§7-6) — 반경 6~8m에서 맞은 사람이 기존 슬라이드 넉백으로 밀리는지. 거리 감쇠의 판별점

**남은 관찰 (모두 낮은 우선순위):**

- [ ] **진입 순간 팔꿈치 Δv 3.2~3.5** — 임펄스 0(진압봉 사망)인데도 나온다. 선 자세 애니메이터 포즈에서 물리로 넘어가는 순간 관절 한계에 걸리는 것으로 보인다. 접촉은 없다. 눈에 보이는 문제로 이어지는지 먼저 확인할 것.
- [x] **어깨·머리의 지속 접촉 충격** — `Shoulder_R ← 충격 27.8~37.9`, `Head ← 20.5`가 여러 스텝 유지된다. **§9-7의 같은 원인으로 확정됐다**(키네마틱 골반이 몸을 지면과 안 맞는 높이에 붙들고 있었다) — 관절 결합으로 함께 사라질 것으로 보고 수정했다. 플레이 검증 항목.

### 9-14. 시체가 맵 밖으로 빠진다 — 안전망이 래그돌한테는 없는 바닥이었다

증상: **폭발 사망 시 시체가 바닥을 뚫고 내려가 돌아오지 않는다.** 죽는 위치에 따라 재현되기도, 안 되기도 했다(그래서 한동안 오너/원격 문제로 오해했다 — 실제로는 위치 문제다).

로그 세 줄이 원인을 좁혔다:

```
진입 — 루트 (14.60, 0.43, 19.01), 골반 (14.61, 1.30, 19.00), 임펄스 (-2.31, 5.03, 1.58), 권한 오너
지면 판정 실패 — 골반 높이(-1836.37)를 쓴다
정착 — 골반 (-31.02, -1836.37, 50.24), 시체 이동 55.28m, 루트 이동 55.24m, 경과 20.00s/타임아웃
```

- **y = −1836m.** 20초 자유낙하 = ½·9.81·20² ≈ 1962m — **20초 내내 아무것도 안 닿았다.**
- **수평 55.28m** = 수평 2.8m/s × 20초. 마찰이 0이라는 뜻이다.
- **시체 이동 55.28 ≈ 루트 이동 55.24** — 캡슐 추종은 정상이었다. 캡슐이 시체를 따라 같이 떨어진 것이다.

범인은 맵 밑에 깔린 500×500m 안전망이다:

```
SafetyNetFloor: layer=2(Ignore Raycast), BoxCollider, y=0, "=== ENVIRONMENT ===" 아래
씬의 비트리거 콜라이더 1420개 → Default(0) 1400 / Interactable(7) 13 / Ignore Raycast(2) 1  ← 이거 하나
```

| | 안전망(layer 2)에 걸리나 |
|---|---|
| CharacterController 캡슐 (Player 루트, layer 0) | ✅ 매트릭스 행0 = `ffffffff` |
| 래그돌 뼈 (layer 10) | ❌ 행10 = `0x00000001` → **Default만** → 통과 |
| `m_groundMask = 1` (지면 탐색) | ❌ Default만 → 안 보인다 |

> **산 사람은 안전망 위에 서지만 시체는 그대로 통과한다.** 그리고 지면 탐색도 못 보므로 정착 게이트(§9-9)가 영원히 안 열려, 배수 타임아웃 20초까지 낙하가 이어진다. **하나의 레이어 실수가 두 증상을 동시에 만든다.**

실 바닥 지오메트리(Default 1400개)가 있는 자리에서 죽으면 정상이고, **실 바닥에 구멍이 있어 안전망이 유일한 바닥인 지점**에서 죽으면 세상 밖으로 나간다 — 재현이 들쭉날쭉했던 이유다.

→ 두 가지를 함께 고쳤다 (**하나만 하면 안 된다** — ①만 하면 시체는 걸리지만 정착이 20초까지 밀리고, ②만 하면 탐색은 되지만 시체가 계속 통과한다):

| | 내용 |
|---|---|
| ① 충돌 매트릭스 | `Ragdoll(10) × Ignore Raycast(2)` 켜기 (`DynamicsManager.asset`) |
| ② `m_groundMask` | `1` → **`5`** (Default + Ignore Raycast) |

안전망을 Default로 옮기는 쪽은 반대다 — 그러면 조준·상호작용 레이가 투명 바닥을 맞는다. 안전망이 layer 2에 있는 것 자체는 옳고, **래그돌이 그걸 몰랐던 것**이 버그다.

**교훈 (NPC 래그돌 §8이 그대로 밟는다):** 전용 레이어를 만들 때 매트릭스는 "충돌해야 할 것"만 보고 켜기 쉽다. 그런데 **바닥은 하나가 아니다** — 실 지오메트리 말고도 안전망·엘리베이터·플랫폼처럼 다른 레이어에 있는 바닥이 있고, 그 목록은 씬을 조회해야 나온다. `Physics.IgnoreLayerCollision`으로 실제 런타임 값을 찍어 보는 것이 프리팹·매트릭스를 읽는 것보다 빠르다.

### 9-15. 시체가 착지 후 1~2초간 미끄러진다 — §9-10의 전제가 이미 바뀌어 있었다

증상: **원격 화면에서 시체가 착지한 뒤 바닥을 스르륵 미끄러져 다른 자리로 이동한다.** 순간이동이 아니라 1~2초에 걸친 슬라이딩이다(그 구분이 진단의 갈림길이었다 — 순간이동이면 §9-6의 재발이고, 슬라이딩이면 당겨오기가 보이는 것이다).

원인은 버그가 아니라 **설계상 감수하던 비용이 실제로 눈에 보인 것**이다. 원격은 오너의 궤적을 받는 게 아니라 자기 궤적을 따로 만든다:

| 어긋남의 출처 | 내용 |
|---|---|
| 임펄스부터 다르다 | `ApplyBlastRagdoll`이 `EvaluateRagdollImpulse(victim.transform.position)`를 **각 피어에서 자기 쪽 값**으로 계산한다. 원격의 `victim.transform.position`은 보간된 스트림이라 폭심 거리가 다르고, **거리 감쇠가 걸려 세기 자체가 갈린다** |
| 물리가 독립이다 | 11-body 시뮬레이션이 피어별로 따로 돌아 접촉 순서 하나로 착지점이 달라진다 |
| 비행 중엔 안 고쳤다 | 그 차이를 착지 후에 **1.5m/s로만** 흡수했다 → 3m 어긋나면 2초간 미끄러진다 |

→ **비행 중에도 당겨온다** (§3-4의 표). §9-10을 뒤집는 것이라 근거를 남긴다:

> §9-10의 측정은 **캡슐이 시체를 못 따라가던 시절**의 것이다 — 그때 원격의 루트는 지면을 타는 접지된 CharacterController였고(실측 시체 38.8m / 캡슐 0.23m), 그걸 향해 당기면 당연히 포물선이 평평해진다. 진짜 교훈은 *"보정하지 마라"* 가 아니라 **"접지된 캡슐을 기준으로 보정하지 마라"** 였다.
>
> 캡슐 추종이 들어온 뒤로 **스트리밍된 루트 = 오너 골반**이다(실측 시체 55.28m / 루트 55.24m — 4cm 오차). 기준이 시체의 궤적 자체가 됐으므로 당겨오는 것이 이제는 옳다. **§9-10의 결론이 아니라 그 전제가 만료된 것이다.**

**교훈:** 측정에 근거한 결론에는 **그 측정이 성립하는 조건**을 함께 적어야 한다. §9-10은 "비행 중 당기지 마라"만 남겨서, 전제를 고친 뒤에도 금지가 살아남아 비용을 계속 물게 했다. 이 문서의 ⚠ 표기가 그 역할을 해야 한다.

**아직 안 고친 같은 계열:**

- **임펄스를 서버가 계산해 RPC에 실어 보내기** — 위 표의 첫 줄은 당겨오기로 덮는 것이고 원인 자체는 남아 있다. "감쇠식은 장치 한 곳"이라는 §4 원칙과도 맞으므로 별건으로 고칠 것.
- **비행 중 루트가 골반 높이만큼 뜬다** — `TickCapsuleFollow`가 루트를 골반에 붙이므로 실측 **+0.87m** 올라가고 비행 내내 `캡슐=공중`이다. 이름표·운반 조준·부활 히트박스가 전부 루트에 붙어 있어 원격에서 몸이 0.9m 뜬 채 날아가는 것으로 보인다. 카메라(커밋 ④)와 같이 볼 것.

### 9-16. 끌려가는 시체가 원격에서 안 따라온다 — **래그돌이 프로젝트의 대전제를 깬다**

이 항목 하나에 이틀이 들어갔다. 증상은 여러 번 모습을 바꿨지만 뿌리는 하나였다.

**증상:** 밧줄로 시체를 끌면 끌리는 본인 화면은 정상인데, **다른 피어에서는 이름표·파티클(루트)만
따라오고 모델(뼈)이 제자리에 남거나 한참 뒤에서 온다.**

#### 뿌리 — "루트를 옮기면 몸이 따라온다"가 더 이상 참이 아니다

이 프로젝트의 **모든** 이동 시스템이 같은 전제 위에 있다 — 호송(#279)·운반(#365)·밧줄(#398)·스폰·
텔레포트가 전부 **루트 트랜스폼을 옮기는 것**으로 구현돼 있다. 그게 성립했던 이유는 캐릭터의 뼈가
애니메이터가 쥔 **키네마틱**이라 트랜스폼 계층을 공짜로 따라왔기 때문이다.

> **래그돌은 정확히 그 전제를 깬다 — 동적 리지드바디는 부모 트랜스폼을 따르지 않는다.**

오너는 자기 물리가 움직임을 만들고 캡슐이 그 몸을 따라가므로(§3-4) 문제가 없다. **원격은 루트 위치만
받는데, 래그돌에서는 루트 위치가 더 이상 몸 위치를 뜻하지 않는다.** 그래서 원격에서만 깨진다.

#### 원격이 "쫓아가게" 만드는 시도는 둘 다 반쪽이다 — 실측으로 확정

| 방식 | 위치 추적 | 흐느적임 | 실측 |
|---|---|---|---|
| 전 뼈를 같은 델타로 평행이동 (`SnapBonesBy`) | ✅ 정확 | ❌ | 뼈 사이 상대 위치가 그대로라 **관절이 느낄 것이 정의상 없다** |
| **골반만** 옮기고 나머지는 관절이 끌게 | ❌ | ✅ | **질량비만큼만 움직인다** |

골반만 옮기는 방식의 실측이 결정적이었다:

```
명령 상한 12 m/s  →  실제 골반 속도 1.5~2.5 m/s   (12~21%)
골반 질량 비율 = 10.94 / 70 = 15.6%              ← 같은 자릿수
루트↔골반 격차: 0.05 → 2.63 → 5.61 → 8.82 → 12.61m   (발산, 회복 없음)
```

**골반(10.9kg)을 텔레포트해도 관절로 묶인 나머지 59kg이 솔버에서 질량 반비례로 되당긴다.** 몸을 5m/s로
옮기려면 골반에 32m/s를 명령해야 하고, 그러면 §9-5의 채찍질이 그대로 재현된다. **상한으로 넘을 수 있는
벽이 아니다.**

#### 결론 — 원격은 정착 후 뼈를 굳힌다

```
오너 : 물리 래그돌. 밧줄이 몸을 끌고, 캡슐이 그 몸을 따라간다 (TickCapsuleFollow)
원격 : 정착 시 전 뼈 키네마틱 → 트랜스폼 계층이 스트리밍된 루트를 따라간다. 쫓아갈 것이 없다
```

**§3-3의 "전부 키네마틱 — 몸이 한 자세로 굳는다"는 오너 기준의 기각이었다.** 원격에서는 어차피 자기
물리가 만든 포즈가 오너와 다르고, **흐느적임보다 위치가 12m 틀리지 않는 것이 훨씬 중요하다.**

잃는 것은 남의 화면에서 시체가 흔들리지 않는 것 하나다. 되찾으려면 `PlayerCarrier.BeginDraggedRpc`를
`SendTo.Owner`에서 전 피어로 바꿔 **원격에도 진짜 밧줄을 묶으면** 된다 — 그때는 위치가 이미 맞으므로
실패해도 되돌리기만 하면 되고, 위치 문제로 돌아가지 않는다. **두 문제를 분리한 것이 이 절의 핵심이다.**

#### 함께 드러난 것 — 정착 후 캡슐은 지면에 앉아야 한다

뼈를 굳히자 시체가 공중에 뜬 채 끌려왔다. `TickCapsuleFollow`가 **정착 후에도** 캡슐을 골반 높이
(지면 위 약 0.3m)에 붙이고 있었기 때문이다. 그러면 ① 캡슐이 내내 `공중`이라 CharacterController가
접지를 못 보고, ② **끌리며 시체가 위아래로 튀는 것이 그대로 루트 높이가 되어 스트림에 실린다** —
굳은 원격 시체가 그 높이를 통째로 탄다.

→ **비행 중에는 3차원 추종, 정착 후에는 수평만 골반을 따라가고 높이는 지면이 준다.**
지면 판정은 `ResolveSettledRootPose`와 같은 함수를 써야 정착 순간에 캡슐이 튀지 않는다.

#### 곁가지로 밟은 것들 (같은 아크)

- **머리가 계속 돈다** — `FollowBodyYaw`를 정착 후에도 돌린 탓. 루트가 돌면 **리지드바디가 없는 뼈**
  (`Neck`·`Spine_01/03`·손·발)는 계층을 따라 도는데 `Head`는 동적이라 안 따라가 목이 비틀린다.
  게다가 yaw를 `headBone.position`에서 계산하므로 되먹임 고리가 생긴다. → **yaw는 비행 중에만.**
- **머리가 덜렁거린다** — 위저드가 `Head`의 `swing2Limit`을 0으로 둔 데는 이유가 있다. 열어 주면
  구(球) 콜라이더가 `angularDamping 0.05`로 자유롭게 돈다. **볼 조인트(어깨·고관절)만 열고 경첩
  (`Elbow`·`LowerLeg`, `swing1Limit == 0`이 신호)은 건드리지 말 것.** 덜렁임의 레버는 관절 한계가
  아니라 **`angularDrag`** 다 — 범위는 두고 속도만 죽이므로 흐느적임을 살린 채 덜렁임만 잡는다.
- **밧줄 하드 리밋이 시체를 튕긴다** — `linearLimitSpring`이 `{0, 0}`이면 위반량을 솔버가 한 스텝에
  해소하며 **11.6m/s**로 튕겨 운반자를 지나친다(손↔골반 `2.12 → 0.33`). 스프링·감쇠를 넣어 부드럽게
  만들면 상시 장력에 가까워진다. ⚠ **이 스프링은 한계 바깥에서만 작동**하므로, 상시 작용해서 시체를
  들어올렸던 `xDrive` 스프링(아래)과 범주가 다르다.
- **관절의 쉼 포즈는 만들어진 순간에 굳는다** — `ConfigurableJoint`를 `Awake`에서 만들면 그 순간의
  상대 포즈(평시 선 자세, 골반이 루트보다 **0.88m 위**)가 기준이 된다. 정착 때 앵커를 옮겨도 관절은
  그 오프셋을 원하므로 **시체를 0.88m 들어올린다.** → **앵커를 옮긴 다음 관절을 만들 것.**
- **위치 스프링으로 시체를 끌 수는 없다** — 수직으로 지고(골반 무게 107N) 수평으로 이기는
  (마찰 412N) 스프링은 존재하지 않는다. 세게 잡으면 뜨고 약하게 잡으면 안 끌린다. 끄는 것은
  힘 문제가 아니라 **제약(밧줄 거리 한계)** 이나 **이동(뼈 평행이동)** 으로 풀어야 한다.

#### 교훈

**증상이 하나로 보여도 피어별로 원인이 다를 수 있다.** 이 아크에서 오너 로그는 내내 정상이었고
(골반이동 ≈ 루트이동, 격차 0.00~0.07m) 원격만 깨져 있었는데, 한동안 오너 쪽만 보며 물리 수치를
만졌다. **§9-13이 "오너·원격 양쪽을 보라"고 이미 적어 둔 것을 지키지 않은 대가다.**

그리고 **물리 수치를 만지기 전에 "이 값이 병목이 맞나"를 먼저 재야 한다.** 질량비 측정 한 번이
"상한을 올리면 된다"는 방향 전체를 폐기시켰다.

### 9-17. 시체를 돌리면 점점 빨라지다 날아간다 — **에너지 펌프**

**증상.** 시체를 밧줄로 끌면서 운반자가 제자리에서 돌면, 시체가 회전할수록 빨라지다가 놓는
순간 멀리 날아간다.

**원심력이 아니다.** 밧줄 앵커는 운반자의 **손**이고(`PlayerTowedMotion.ResolveRopeAnchor`),
제자리 회전에서 손이 그리는 원은 지름 0.8m 남짓이다. 구속은 "앵커 중심 반경 2m 구" 하나뿐이라
구가 0.4m 평행이동하면 시체도 최대 0.4m만 움직이면 된다. **회전 자체는 시체에 속도를 줄 이유가
없다.**

**실제 원인은 반주기 비대칭이다.**

| 반주기 | 밧줄 | 한계 스프링 | 한계 감쇠 |
|---|---|---|---|
| 손이 멀어질 때 | 팽팽 | 당긴다 (+에너지) | 작동 |
| 손이 가까워질 때 | 늘어짐 | **0** | **0** |

한계 스프링은 설계상 **한계 바깥에서만** 작동한다(그게 "스프링이 아니라 거리 제한"인 이유다).
그래서 늘어진 반주기에는 에너지를 뺄 수단이 **하나도 없다** — 뼈 `linearDamping`이 0이었기
때문이다. 게다가 3000/600은 몸 전체 70kg 기준 임계 2√(3000×70)≈916에 대해 ζ≈0.65로
**부족감쇠**라, 팽팽해질 때마다 오버슛으로 속도를 얹었다. 넣는 반주기는 있고 빼는 반주기가
없으니 회전 주기마다 에너지가 누적된다.

`600`을 임계보다 **일부러 낮게** 잡은 것은 "끌릴 때 몸이 살짝 출렁여 흐느적임이 산다"는 의도였다.
그 의도 자체가 펌프의 연료였다.

**고친 방법 — 주입을 막고 배출구를 연다. 둘은 짝이다.**

- 한계를 **과감쇠**로: 강성 3000 → 1500, 감쇠 600 → 1000 (ζ≈1.5). 오버슛이 사라진다.
- 뼈에 **밧줄 구간 한정** 감쇠: `linearDamping` 0 → 0.6, `angularDamping` 0.05 → 0.6.
  늘어진 반주기에도 에너지가 빠진다.

**⚠ 감쇠를 상시로 걸면 안 된다.** 사망 직후의 비행은 임펄스만이 입력인 **탄도**여야 하고
(§9-11의 반대 방향 — 오히려 더 날려야 한다), 상시 감쇠는 그 구간을 같이 갉아먹는다. 그래서
감쇠의 수명을 밧줄의 수명과 정확히 일치시켰다: `ApplyRopeTuning` ↔ `DetachRope`.

**흐느적임은 잃지 않는다.** 그건 한계 스프링의 오버슛이 아니라 **손의 걸음 흔들림**이 만든다
(§9-7에서 앵커를 루트에서 손으로 옮긴 이유가 그것이다) — 과감쇠로 바꿔도 그쪽은 그대로 남는다.

> ⚠ **이 수정이 잡는 것은 "제자리에서 도는" 경우뿐이다.** 운반자가 *달리면서* 원을 그리면
> 원인이 다르고 감쇠로는 못 막는다 — §9-18.

#### 교훈

**"세기 노브"를 찾기 전에 에너지가 어디로 들어오고 어디로 나가는지를 세라.** 후보는 강성·감쇠·
밧줄 길이·뼈 감쇠 넷으로 보였지만, 실제로는 *주입*과 *배출* 두 자리였고 배출이 아예 비어 있었다.
한쪽만 만졌으면 증상이 옮겨 다녔을 뿐 사라지지 않았을 것이다.

**"조건부로만 작동하는 힘"은 반대 조건에서 무슨 일이 나는지를 같이 적어야 한다.** 한계 스프링의
"바깥에서만 작동한다"는 성질은 시체가 안 뜨게 해 주는 **장점**으로만 기록돼 있었고, 그 이면인
"안쪽에서는 감쇠도 없다"는 아무 데도 적혀 있지 않았다.

### 9-18. 달리며 원을 그리면 여전히 날아간다 — **밧줄은 투석기다**

**증상.** §9-17을 고친 뒤 제자리 회전에서는 시체가 얌전해졌는데, 운반자가 **달리면서** 원을
그리면 여전히 시체가 점점 빨라져 날아간다. 실제로 `m_breakDistance`(8m)에 걸려
`ServerDrop("대상을 놓침 — 너무 멀어짐")`으로 운반이 끊겼다. (물리 관절이 끊긴 것이 아니다 —
`ConfigurableJoint.breakForce`는 무한대다. 안전망이 제대로 동작한 것이다.)

**§9-17과 다른 메커니즘이다.** 그쪽은 팽팽↔늘어짐의 반주기 비대칭이 만드는 *공진*이었다.
이쪽은 그냥 **투석기**다:

> 밧줄 장력의 방향은 항상 앵커 쪽(반경 방향)이다. 그런데 **앵커가 움직이면 그 장력이 일을 한다** —
> 축을 끌고 다니면서 추를 가속하는 것이 투석기의 원리 그대로다. 회전이 빨라질수록 장력이
> 하는 일은 **ω²**로 커진다.

**그래서 감쇠로는 원리적으로 못 막는다.** 선형 감쇠가 빼는 에너지는 **v**에 비례한다.
입력이 ω², 배출이 v면 빠르게 돌수록 입력이 이긴다 — 감쇠를 올려도 **날아가기 시작하는 회전속도가
밀릴 뿐 상한이 생기지 않는다.** 현실에서 이 역할을 하는 것은 지면 마찰(약 412N)인데,
장력이 커지면 시체가 손 높이(1.1m)로 들려 **그 마찰마저 사라진다.**

**고친 방법 — 봉투(envelope)를 씌운다.** ω와 무관하게 성립하는 값이 필요하므로 하드 캡을 건다:
`m_ropeMaxSpeed = 8`(스프린트 속도와 동일), 밧줄에 묶인 동안에만, 방향은 두고 크기만 자른다.

근거는 취향이 아니다 — **끌려가는 시체가 끄는 사람보다 빠를 이유가 없다.** 넘는 만큼은 전부
솔버가 만들어 낸 슬링 에너지다. 캡에 걸리면 시체는 회전 바깥으로 뻗어나가는 대신 뒤처지고,
밧줄이 늘어난 채 안쪽 궤도로 끌려온다 — "몸은 휘두를 수 없다"가 그림으로 나온다.

`k_maxDepenetrationVelocity`·`m_alignSnapDistance`와 같은 계열이다: **정상 동작에서는 걸리지 않아야
하고, 자주 걸리면 상한을 올릴 게 아니라 왜 걸리는지를 봐야 한다.**

#### 남은 것 (후속)

**시체 무게가 운반자를 안 늦춘다.** `RopeDragLoad`(#398)는 NPC 밧줄 견인에만 붙어 있어,
70kg 시체를 끌면서도 스프린트로 원을 그릴 수 있다. 현실에서 슬링이 안 생기는 진짜 이유가
"그렇게 못 돌기 때문"이므로, 이걸 붙이면 캡에 걸릴 일 자체가 줄어든다. 캡은 그래도 남겨야 한다 —
무게는 ω를 줄일 뿐 상한을 보장하지 않는다.

#### 교훈

**"같은 증상"이 두 번 나오면 원인이 같다고 가정하지 말 것.** 제자리 회전과 달리며 회전은 눈에는
똑같이 "원심력으로 날아감"이었지만, 하나는 공진이고 하나는 투석기였다. §9-17의 수정이
제자리 쪽만 없앤 것이 그 증거였다.

**입력과 배출의 차수(order)를 비교하라.** "감쇠를 올리면 되지 않나"는 ω² vs v를 세 보기 전에는
그럴듯해 보인다. 차수가 다르면 계수 튜닝은 임계점을 옮길 뿐 문제를 없애지 못하고, 그럴 때는
**계수가 아니라 봉투**가 답이다.

### 9-19. 폭발 사망자가 원격에서만 제자리에 무너진다 — **부활로 오인된 래그돌**

**증상.** 호스트가 죽으면 전 피어에서 잘 날아가는데, **클라이언트가 죽으면** 아무 화면에서도 안
난다. 시체가 살짝 들썩이다 그 자리에 눕는다.

**실측 (2026-08-06).**

```
[클라 = 죽은 본인 · 오너]
[진입] 신규 오너 | 임펄스 8.87 | 골반v 9.71 | 사망=False 원인=None   ← 임펄스가 먼저 왔다
[취소] 오너 상태=Ragdoll 진입후 0.00s | 사망=False 원인=None → ExitToAnimator(부활로 처리)
[착지] 실측 수평 0.04m 체공 0.00s | 이론 8.58m | 0 %
[진입] 신규 오너 | 임펄스 0.00 | 사망=True 원인=Die                  ← 사망이 뒤늦게 도착
[착지] 실측 수평 0.09m 체공 1.24s                                    ← 임펄스 없는 붕괴

[호스트 = 원격 관찰자]
[진입] 신규 원격 | 임펄스 8.87 | 골반v 9.71 | 사망=True 원인=Die     ← 취소 없음
[착지] 원격 | 실측 수평 0.12m 정점 +0.76m 체공 3.23s | 이론 8.58m | 1 %
```

**원인.** `PollDeath`의 `!dead` 분기는 **"살아 있는데 래그돌이면 부활한 것"** 이라는 전제였다.
그 전제가 원격에서 깨진다:

| 경로 | 실려 오는 것 | 오브젝트 |
|---|---|---|
| 사망 사실 | `PlayerIncapacitation`의 NetworkVariable | 플레이어 |
| 폭발 임펄스 | `BombDevice`의 ClientRpc | 폭탄 |

**다른 오브젝트라 도착 순서가 보장되지 않는다.** 임펄스가 먼저 오면 그 피어는 "아직 살아 있는
대상이 래그돌 중"을 보고 방금 시작한 비행을 **부활로 오인해 취소한다.**

`EnterRagdoll`은 이 순서 문제를 알고 있었고 멱등으로 막아 두었다 — 그런데 막은 것은
**"사망 → 임펄스"** 한쪽뿐이었다. 반대 순서는 `PollDeath`가 뚫려 있었다.

**호스트가 멀쩡했던 이유.** 호스트는 서버라 `Cause`가 동기화값이 아니라 로컬 진실값이고
(`IsSpawned && !IsServer ? synced : m_cause`), `TakeDamage` → `Incapacitate(Die)`가
`NotifyBlastDeaths`보다 **먼저 동기적으로** 실행된다. 순서가 뒤집힐 수가 없다.

**호스트 화면이 안 났던 것은 별개 버그가 아니다.** 원격은 포즈만 로컬 물리로 만들고 궤적은
오너의 스트리밍된 루트에서 받는다(§10-3). 클라의 래그돌이 취소돼 `TickCapsuleFollow`가 안 돌았으니
루트가 제자리였고, `TickAlignBonesToRoot`가 날아가려는 뼈를 **충실히 되끌었다.** 위 로그의
"정점 +0.76m인데 수평 0.12m"가 그 지문이다 — 뜨긴 떴는데 수평으로 못 갔다.

**고친 방법 — 시간이 아니라 인과로 막는다.**

```
부활은 죽음을 본 뒤에만 성립한다.
```

`m_sawDeathThisEpisode`를 두고, 이번 에피소드에서 사망을 한 번이라도 관측한 뒤에만 `!dead`를
부활로 인정한다. 지연에는 상한이 없으므로 "N초 기다린다"로는 못 맞춘다. 임펄스는 서버가 사망을
확정한 대상에게만 나가므로(`BombDevice.m_deathBuffer`) 사망 동기화는 **반드시 뒤따라 온다.**

유예(`k_deathSyncGraceSeconds = 1`)는 안전망일 뿐이다 — 대상이 아주 빠르게 되살아나 이 피어가
`Die`를 아예 못 보고 `None`만 받는 병리적 순서에서 시체가 래그돌에 영구히 갇히는 것을 막는다
(`ExitToAnimator`를 부르는 곳이 `PollDeath` 하나다).

**검증 (같은 날, 클라 사망).**

```
[클라 = 오너]   [착지] 실측 수평 9.05m 정점 +2.31m | 이론 8.66m | 104 %
[호스트 = 원격] [착지] 실측 수평 9.10m 정점 +2.26m | 이론 8.66m | 105 %
```

`[래그돌/취소]`가 아예 뜨지 않았다. 클라 진입 로그에는 **여전히 `사망=False 원인=None`이 찍힌다** —
순서 경쟁은 그대로 있는데 결과가 깨지지 않는다. 순서를 맞춘 것이 아니라 순서와 무관하게 만들었으므로
의도한 대로다.

부수적으로 **§10-3이 실측으로 확인됐다**: 뼈를 동기화하지 않고 각 피어가 로컬로 돌린 시뮬레이션이
9m를 날고도 **5cm 차이로 수렴**했다. "입력이 같으면 결과가 대체로 같다"는 전제가 이 거리에서도
성립한다.

#### 교훈

**"A이면 B다"가 로컬에서 참이라고 네트워크에서 참인 것이 아니다.** "살아 있는데 래그돌 = 부활"은
단일 피어에서는 반박할 수 없는 명제였다. 두 사실이 **서로 다른 오브젝트로** 도착하는 순간
"아직 도착하지 않았을 뿐"이라는 세 번째 경우가 생긴다.

**멱등을 넣었다면 반대 순서도 같이 확인하라.** `EnterRagdoll`에는 순서 문제를 정확히 설명하는
주석이 이미 있었고 한쪽은 막혀 있었다. 뚫린 쪽은 **같은 파일 200줄 아래**에 있었다.

**증상이 나온 피어가 원인이 있는 피어가 아니다.** "호스트 화면에서 안 난다"로 시작했지만 고칠
곳은 클라이언트였다. 원격이 오너에게서 궤적을 받는 구조에서는 **원격의 증상이 오너의 상태를
비추는 거울**이므로, 원격만 보고 원격을 고치려 들면 계속 헛짚는다.

### 9-20. 유예가 들어오며 폭발 사망 래그돌이 조용히 깨져 있었다 (2026-08-27, #903)

**증상** — 폭탄에 죽으면 래그돌로 날아갔다가 약 1초 뒤 **다시 일어나** Knockdown 자세로 누웠다.

**성립 조건** — #725가 HP 0을 `Die`가 아니라 `Down`(유예 60초)으로 돌렸다. `BombBlast`는 여전히
`CurrentHp == 0`인 사람을 사망자로 보고 임펄스 RPC를 보내는데, `PollDeath`는 `IsDead || IsLaunched`만
본다 → `wantsRagdoll`이 거짓이라 `m_sawDeathThisEpisode`가 서지 않고, `m_awaitingDeathSeconds`가
`k_causeSyncGraceSeconds`(1초)를 넘기면 `§9-19`의 가드가 **"진짜 부활"로 판정해** `ExitToAnimator`를 부른다.

**즉 `§9-19`의 가드는 정상 동작했다.** 임펄스는 오는데 사망이 영영 오지 않으므로, 가드 입장에서
"1초 안에 안 죽었으면 부활"은 옳다. 버그는 **그 위쪽에서 `Die`를 세우지 않게 된 것**이고, 틈의
정체는 사망 판정이 `CurrentHp == 0`(체력)과 `IsDead`(원인) **두 값으로 갈려 있던 것**이다.

**고친 방법** — `PlayerRagdoll`을 **한 줄도 안 고쳤다.** 진입점을 `PlayerHealth.TakeLethalDamage`로
바꿔 폭발이 HP 0에서 곧바로 `Die`를 세우게 했다. 그러면 전 피어의 폴링이 그것을 관측해
`m_sawCauseThisEpisode`가 서고 오인 취소가 사라진다. GDD 6-4가 원래 적어 둔 "폭심 즉사"로 돌아간 것이다.

> **일반화되는 교훈**: `§9-19`의 계약("부활은 죽음을 본 뒤에만 성립한다")은 **위쪽에서 누가 `Die`를**
> **세우는가가 바뀌면 조용히 반대로 작동한다.** 가드를 고칠 자리가 아니라, 가드가 기다리는 사실이
> 여전히 오는지 확인할 자리다. 전문은 [903-instant-death.md](903-instant-death.md).

**함께 바뀐 것** — 차량 즉사도 이제 래그돌 임펄스를 보낸다. `§3-2`의 넉백 이중 적용 방지와 같은 규칙을
따르되, **오너 지정 RPC를 쓸 수 없다**는 제약이 새로 붙었다(사망 진입이 소유권을 서버로 옮기므로 —
[player-ragdoll.md §8](player-ragdoll.md)).

### 9-21. 임펄스는 도착했는데 **다음 프레임에 지워졌다** — 권위 이관 폴링 (2026-08-31)

**증상** — 폭탄에 죽은 플레이어가 폭심 반대로 날아가지 않고 **제자리에서 힘없이 무너진다.**
`§9-19`(부활 오인)도 `§9-20`(유예)도 아니다 — 래그돌은 정상적으로 켜지고 취소도 안 되며,
로그상 사망자 수집·임펄스 계산·RPC 발행이 전부 정상이다.

**비대칭이 진단의 전부였다.** 호스트 자기 캐릭터는 날아가고 **클라이언트 캐릭터만** 제자리다.
그리고 홈런 진압봉(#815)은 클라이언트에서도 멀쩡히 날아간다. 세 사실을 겹치면 남는 차이는 하나뿐이다
— **사망은 소유권을 서버로 옮기고(#763/#865), 비행(`Launched`)은 옮기지 않는다.**

**성립 조건** — `PlayerRagdoll.m_hadMoveAuthority`는 기본값 `false`이고 `TickAuthorityHandover`
**안에서만** 갱신됐다. 클라 소유 플레이어의 **서버 쪽 인스턴스**에서는 이 래치가 계속 `false`다.

1. `TakeLethalDamage` → `Incapacitate(Die)` → `ApplyDeathOwnership` → `ChangeOwnership(Server)`
   — 같은 호출 스택에서 동기 실행. 이 순간 서버의 `HasMoveAuthority`가 `true`가 된다.
2. 이어서 `BombBlast.NotifyBlastDeaths` → `EnterRagdoll(impulse)`. 뼈가 비키네마틱이 되고
   `ApplyImpulse`가 제대로 걸린다. **여기까지는 옳다.**
3. **다음 `Update`**의 `TickAuthorityHandover`가 `false → true` 전이를 뒤늦게 보고
   `ReleaseBonesToPhysics()`를 다시 부른다 → `RagdollRig.SetKinematic(false)` →
   `SetBodyKinematic(body, false)`의 `body.linearVelocity = Vector3.zero`가 **임펄스를 지운다.**

`SetBodyKinematic`이 양방향에서 속도를 지우는 것은 의도된 사양이다(ragdoll-rig 문서 §6) — 잘못은
**이관이 이미 끝난 진입을 이관으로 다시 세는 것**에 있었다.

**깨진 전제** — `TickAuthorityHandover`의 주석은 *"정상 경로에서는 걸리지 않는다 — 이관은 언제나
`Animated` 구간에서 끝난다"*고 적고 있었다. 그 말은 **래그돌 진입이 `PollRagdollCause`로만 일어날 때**
참이다. 폭발·차량은 자기 `Update`(폭탄/차 쪽)에서 진입시키므로 **진입이 이관 감지보다 먼저**다.

**고친 방법** — `ReleaseBonesToPhysics()` 안에서 `m_hadMoveAuthority = HasMoveAuthority`를 세운다.
이 함수는 진입과 이관 양쪽에서 불리므로 *"뼈를 지금 권위 기준으로 배선했다"*는 사실이 한 곳에
기록된다. 진짜 비행 중 이관(비행 중 다운 등)은 그대로 잡힌다 — 그때는 배선 시점의 권위와 현재
권위가 실제로 다르다.

> **일반화되는 교훈**: 상태 전이를 "직전 값과 다른가"로 감지하는 래치는, **그 상태를 소비하는 코드가**
> **폴링 밖에서도 불릴 수 있게 되는 순간** 조용히 한 박자 늦는다. 래치를 세우는 자리는 폴링이 아니라
> **그 상태를 실제로 반영한 자리**여야 한다.

**함께 고쳐진 것** — 차에 치인 즉사(#903)도 같은 경로라 클라 캐릭터가 안 날아가고 있었다.
이 한 줄로 같이 낫는다.

## 10. 설계 계약 (2026-08-06 재정리)

§9까지의 구현은 증상이 나올 때마다 한 겹씩 얹은 결과였다. 여기서 **기대 결과부터 다시 쓰고**,
거기서 구조를 역산한다. 코드보다 이 절이 먼저다.

### 10-0. 뿌리 — **한 계층에 이동 시스템이 두 개 있다**

§9의 함정 여러 개가 서로 다른 증상으로 보였지만 뿌리는 하나다. 이 절이 그것이고, **아래 모든
선택지는 이 결정 위에 놓인다.**

```
Player (루트)
├── CharacterController   ← 평시의 이동 시스템
└── Root/Hips/...         ← 사망 시의 이동 시스템 (Rigidbody 11개 + CharacterJoint 10개)
```

**평시:** `CharacterController`가 주인이다. 뼈는 키네마틱이라 애니메이터가 포즈만 얹고, **이동은
트랜스폼 계층이 공짜로 전달한다.** 이 프로젝트의 모든 이동(호송 #279·운반 #365·밧줄 #398·스폰·
텔레포트)이 "루트만 옮기면 끝"으로 짜여 있는 근거가 이것이다.

**사망:** 주인이 **뼈**로 넘어간다. 뼈가 지형과 충돌하고 물리에 구속된다. 그런데 **동적 리지드바디는
부모 트랜스폼을 따르지 않으므로, 위의 "루트만 옮기면 끝"이 그 순간 거짓이 된다.**

**부활:** 다시 `CharacterController`가 주인. 뼈는 키네마틱으로 복귀.

#### 이 결정이 흩어져 있었던 대가

같은 뿌리를 **증상별로 네 번** 따로 처리했다:

| 증상 | 그때 적은 곳 | 실제 원인 |
|---|---|---|
| 쓰러지는 순간 튐 | §9-1 `IgnoreCollision` 세 곳 재적용 | 캡슐과 뼈가 **둘 다 물리 오브젝트**라 서로 충돌한다 |
| 정착 후 시체가 캡슐에 끌려간다 | §9-4 / §9-7 | 캡슐이 움직이면 **계층이 키네마틱 골반을 끈다** |
| 캡슐이 시체를 못 따라간다 | §9-11 스윕+텔레포트 | 캡슐은 `Move()` 스윕이라 **탄도 시체와 갈 수 있는 곳이 다르다** |
| 원격에서 모델이 안 온다 | §9-16 | 원격은 **루트 위치만** 받는데 그게 더 이상 몸 위치가 아니다 |

**규칙으로 박는다:** 사망 중 위치의 주인은 **뼈**이고, `CharacterController`는 *"이 플레이어가 어디
있나"* 를 기록하는 **대리값**이다. 대리값은 몸을 따라가되, **몸을 밀어서는 안 된다.**

#### 그래서 따라 나오는 선택지 — 사망 중 CharacterController를 끈다

지금은 캡슐을 **켜 둔 채** `Move()` 스윕 + 잔차 텔레포트로 골반을 따라간다. 끄면 위 표의 앞 세 줄이
**구조적으로 사라진다:**

- 캡슐이 물리 오브젝트가 아니게 되므로 **뼈와 충돌하지 않는다** → §9-1의 세 곳 재적용이 통째로 불필요
- 스윕이 아니므로 **지형에 막혀 추종에 실패할 수 없다** → §3-4의 스윕+텔레포트 혼합이 불필요
- 계층이 키네마틱 뼈를 끄는 문제는 남지만, 캡슐이 **뼈를 따라가는 쪽**이라 방향이 반대다

**이미 이 프로젝트에 있는 패턴이다.** 호송(#279)이 정확히 그렇게 한다:

```csharp
// PlayerTowedMotion.BeginEscortFollow
m_movement.SetControllerEnabled(false);   // 끄고
transform.position = ...                  // 직접 옮긴다
```

`PlayerMovement.SetControllerEnabled`가 애초에 그것 때문에 있는 함수다(§3-4).

**대가:** 캡슐이 지형을 존중하지 않는다. 그런데 §3-4가 이미 *"몸은 뼈이고 뼈의 충돌은 그대로다.
캡슐은 대리값이라 몸이 있는 자리에 놓는 것은 물리를 속이는 것이 아니다"* 로 정리해 뒀다 —
**사망 중 캡슐이 지형을 존중할 이유가 없다.**

**확인할 것:** ① 부활 시 캡슐을 켜는 지점에서 지면에 제대로 앉는가(§9-4의 `CapsuleBottomOffset`)
② 캡슐이 꺼진 동안 루트 콜라이더에 의존하는 조준·상호작용이 있는가

#### 두 축을 분리한다

이 결정을 박아 두면 남은 논의가 **서로 얽히지 않는 두 축**으로 갈린다. 지금까지 이 둘을 같이
논의해서 원인이 계속 엉켰다:

| 축 | 질문 | 후보 |
|---|---|---|
| **A. 대리값(캡슐)을 어떻게 다루나** | 켠 채 스윕? 끄고 대입? | §10-0의 "끈다" |
| **B. 원격에서 뼈를 어떻게 움직이나** | 굳힐까 / 같은 입력으로 재현할까 / 골반만 물릴까 | §10-3, 그리고 아래 선택지 ①~⑥ |

---

### 10-1. 기대 결과

| # | 요구 | 누가 보는가 |
|---|---|---|
| **R1** | HP 0 → 래그돌 시체가 된다 | 전원 |
| **R2** | 물리로 날아갈 때 **흐느적거리며** 난다 | 전원 |
| **R3** | 다른 플레이어가 밧줄로 끌고 다닐 수 있다 | — |
| **R4** | **끌릴 때에도 흐느적거리며 따라온다** | 전원 |

> **R4가 이 설계의 분기점이다.** 끄는 사람은 시체의 **원격 피어**다(자기 시체를 자기가 끌 수는 없다).
> 따라서 **원격에서 흐느적임이 나와야 한다** — 이 한 줄이 아래 §10-3의 결론을 강제한다.

### 10-2. 협상 불가능한 불변식

요구가 아니라 **이 프로젝트의 구조가 이미 정해 놓은 것**들이다. 설계는 이것들을 어길 수 없다.

| | 불변식 | 근거 |
|---|---|---|
| **I1** | **루트가 시체가 있는 자리를 가리켜야 한다** | 이름표·`ReviveHitbox`(layer 7, 조준으로 시체를 집는 콜라이더)·`NavMeshObstacle`·운반 대상 판정이 전부 루트에 붙어 있다. 갈리면 "보이는 시체를 조준해도 안 잡힌다"(§9-11) |
| **I2** | **뼈는 동기화하지 않는다. 루트 트랜스폼 하나만** | 결정 4 |
| **I3** | **위치 권한은 오너** | NetworkTransform 오너 권한. 서버가 남의 캐릭터를 옮겨도 되돌아온다 |
| **I4** | 부활 시 애니메이터로 복귀 | 정착 포즈 → 블렌드 → `StandUp` (§3-6) |

### 10-3. 핵심 결론 — 모든 피어가 **같은 입력으로 같은 시뮬레이션**을 돌린다

R2·R4는 "각 피어에서 진짜 물리가 돌아야 한다"를 뜻한다. I1은 "그 결과가 피어마다 크게 갈리면
안 된다"를 뜻한다. 둘을 동시에 만족시키는 방법은 하나뿐이다:

> **피어마다 궤적을 맞추려 들지 말고, 애초에 같은 입력을 주고 잔차만 보정한다.**

시체의 움직임을 정하는 입력은 넷이고, **넷 다 전 피어가 가질 수 있다**:

| 입력 | 지금 | 되어야 할 것 |
|---|---|---|
| 진입 시점·자세 | `Die` 동기화값 폴링 — 전 피어 동일 ✅ | 그대로 |
| **임펄스** | 각 피어가 **자기 쪽** victim 위치로 계산 → 거리 감쇠 때문에 **세기부터 갈린다** ❌ | **서버가 계산해 RPC로 실어 보낸다** |
| **밧줄 제약** | 오너에만 관절이 생긴다(`SendTo.Owner`) ❌ | **전 피어에 같은 관절**. 앵커는 운반자의 손(그 자체가 동기화된 트랜스폼) |
| 지형 | 전 피어 동일 ✅ | 그대로 |

**여기서 이전에 막혔던 딜레마가 풀린다.** §9-16은 원격 정렬의 두 방식이 각각 반쪽이라고 적었다:

- 전 뼈 평행이동 → 위치는 맞지만 **포즈가 정의상 굳는다**
- 골반만 → 흐느적이지만 **질량비(12~21%)만큼만 움직여 발산한다**

**그건 원격에 "몸을 움직이는 주체"가 없었기 때문이다.** 평행이동이 유일한 동력이면 포즈가 굳는 게
당연하다. 로컬 물리가 몸을 움직이고 있으면, **평행이동은 동력이 아니라 잔차 보정일 뿐이고 포즈는
살아 있다.** 같은 도구가 역할이 바뀌면 결론도 바뀐다.

### 10-4. 역할 × 단계

```
전 피어 공통 : 같은 입력으로 자기 래그돌을 돌린다. 흐느적임은 여기서 나온다.
오너 추가    : 캡슐이 시체를 따라간다 → 그 위치가 루트로 스트리밍된다 (I1·I3)
원격 추가    : 로컬 시체가 스트리밍된 루트에서 표류하지 않게 잔차만 보정한다
```

| 단계 | 오너 | 원격 |
|---|---|---|
| **비행** | 물리(임펄스). 캡슐이 골반을 **3차원** 추종 | 물리(**같은** 임펄스). 잔차 보정 — 3차원, 부드럽게 |
| **정착** | 물리 유지. 캡슐이 골반을 **수평만** 추종, 높이는 지면이 준다 | 물리 유지. 잔차 보정 — 수평만 |
| **끌림** | **밧줄 관절**이 물리로 끈다. 캡슐 추종은 위와 같다 | **같은 밧줄 관절**이 물리로 끈다. 잔차 보정 |
| **부활** | 전 뼈 키네마틱 → 정착 포즈에서 애니메이터로 블렌드 | 동일 |

읽는 법 — **가로줄이 아니라 세로줄이 축이다.** 오너 열은 "위치를 만든다", 원격 열은 "표류를
막는다". 지금 코드가 어려운 이유는 이 축이 상태 기계 안에 흩어져 있어서다.

### 10-5. 잔차 보정의 규칙

이전 시도가 실패한 이유가 전부 여기에 있으므로 규칙으로 못박는다.

1. **보정은 동력이 아니라 표류 방지다.** 정상 동작에서 잔차는 작아야 하고, 크면 그건 입력이
   안 맞는다는 신호지 보정을 세게 할 일이 아니다.
2. **전 뼈를 같은 델타로 옮긴다.** 골반만 옮기는 것은 질량비만큼만 먹는다(§9-16 실측).
3. **속도 상한을 둔다.** 루트가 병리적으로 튈 때 그 점프가 뼈로 전달되면 안 된다.
4. **비행 중엔 3차원, 착지 후엔 수평만.** 착지 후 높이의 주인은 각 피어의 지형이다.
5. **옮기는 경로는 `ClampByWall`을 지난다.** `position` 대입은 텔레포트라 충돌을 무시한다(§3-4 표).
6. **잔차가 임계를 넘으면 스냅한다.** 그 상태는 이미 눈에 띄게 틀렸으므로 포즈 보존이 의미 없다.

### 10-6. 인수 조건

새로 쓰든 고치든, **§9의 16개를 전부 만족해야 한다.** 코드만 보면 이유가 안 보이는 것들이므로
구현 전에 훑을 것 — 특히:

- §9-1 `IgnoreCollision`은 콜라이더 토글로 지워진다 (세 곳에서 재적용)
- §9-2 관절 `projection`은 켜지 않는다
- §9-3 `solverIterations`·`maxDepenetrationVelocity`는 프리팹에 저장되지 않는다 (런타임 적용)
- §9-4 정착 순서: 포즈 캡처 → 키네마틱 → 루트 이동(오너만) → 포즈 복원
- §9-9 지면 판정 없이 타임아웃만으로 정착하면 시체가 허공에 굳는다
- §9-12 새 `[SerializeField]` 노브는 **프리팹에도 명시적으로 박는다**
- §9-14 지면 마스크에 안전망 레이어(`Ignore Raycast`)가 들어가야 한다
- §9-16 골반만 끌어서는 위치를 못 옮긴다 / 정착 후 캡슐은 지면에 앉는다

그리고 **작업 규칙 하나** — 물리 수치를 만지기 전에 **그 값이 병목인지 먼저 잰다.** 질량비 측정
한 번이 "상한을 올리면 된다"는 방향 전체를 폐기시켰다. 이 규칙을 안 지킨 것이 §9-16 아크의 절반이다.

### 10-7. 현재 코드와의 차이

| | 현재 | §10 |
|---|---|---|
| 임펄스 | 각 피어가 자기 위치로 계산 | **서버가 계산해 RPC** |
| 밧줄 | 오너에만 관절 (`SendTo.Owner`) | **전 피어에 관절** |
| 원격 정착 후 | **전 뼈 키네마틱**(굳음) | 물리 유지 + 잔차 보정 |
| 원격 정렬 | 비행 중에만 | 전 구간, 단 **보정 수준**으로 |

**R4를 만족하려면 이 넷이 다 바뀌어야 한다.** 반대로 R4를 포기하면 현재 구조가 그대로 답이다 —
그 경우 이 절은 "원격은 굳힌다"로 끝난다.

## 11. 구조 분리 — NPC 래그돌을 위한 준비 (2026-08-06)

`PlayerRagdoll`이 1545줄(코드 796 / 주석 531)까지 자라 있었고, NPC에도 래그돌을 붙이기로 하면서
**공통이 될 부분을 먼저 갈랐다.**

### 11-1. 자른 선 — "뼈를 물리에 넘기는 것" vs "누가 위치를 쥐나"

| | Player | NPC |
|---|---|---|
| 이동 프록시 | CharacterController | **NavMeshAgent** |
| 위치 권위 | **오너** 권한 NetworkTransform | **서버** 권한 |
| 기존 밧줄 | — | 서버가 `transform.position` 직접 대입 |
| 사망 | `IncapacitationCause.Die` | **없음** — HP 0 → Stun |
| 리그 | Synty (FP 팔 때문에 두 벌) | 같은 본 이름, 한 벌 |

프록시와 권위가 **둘 다** 다르므로 상속(추상 베이스)으로는 공유되는 실체가 남지 않는다 —
거의 전부 `abstract`가 된다. **컴포지션**으로 간다.

```
Assets/Scripts/Common/Ragdoll/
  RagdollRig    뼈·스킨 수집, 키네마틱 토글, 임펄스, 감쇠, 속도캡,
                포즈 캡처/복원, 블렌드, 정착 판정용 평균속도, 몸 방향 yaw
  RagdollRope   관절 밧줄 (앵커·튜닝·수명)

Assets/Scripts/Player/View/
  PlayerRagdoll 상태 기계, 사망 폴링, 캡슐 추종, 원격 정렬,
                정착 루트 포즈, 기상 블렌드 오케스트레이션
```

**판별 기준은 하나다.** `RagdollRig`·`RagdollRope`에는 `IsOwner`·`NetworkObject`·
`CharacterController`가 **한 번도 나오지 않는다.** 나오기 시작하면 분리가 무너진 것이다.

### 11-2. 옮기면서 걸린 것

- **`TryGetBodyYaw`에 클립 보정이 섞여 있었다.** `m_rootYawOffset`은 `Knockdown_StandUp`이 어느 쪽을
  머리로 보는지에 맞추는 값이라 **그 리그의 클립 사정**이다. 리그는 순수한 몸 방향만 내고 보정은
  소유자가 얹도록 갈랐다 — 안 그러면 NPC가 다른 기상 클립을 쓸 때 플레이어 값이 따라온다.
- **같은 GameObject 위 컴포넌트의 `Awake` 순서는 보장되지 않는다.** `RagdollRope`와 `PlayerRagdoll`이
  둘 다 자기 `Awake`에서 뼈를 요구하는데, 리그가 나중에 깨어나면 앵커가 안 만들어지거나 캡슐 충돌
  무시가 안 걸린 채 **조용히** 넘어간다. 실행 순서를 프로젝트 설정으로 강제하는 대신
  `RagdollRig.EnsureCollected()`를 멱등으로 두고 소비자가 첫머리에서 부른다.

### 11-3. 밧줄은 합치지 말 것

NPC에도 밧줄이 있지만(`NpcController.Rope`) **메커니즘이 다르다** — 그쪽은 서버가
`transform.position`을 대입하고 NetworkTransform이 복제한다. 래그돌이 된 몸은 동적 리지드바디라
그 방식이 통하지 않아(부모 트랜스폼을 따르지 않는다) 관절 방식이 필요했다.
**두 방식을 하나로 우겨넣지 말 것** — 갈리는 기준은 "대상이 래그돌이냐 아니냐"다.

### 11-4. NPC 래그돌의 선행 과제 (코드 구조가 아니다)

1. **리그 빌드가 Player 전용이다.** `PlayerRagdollSetup.k_prefabPath`가
   `Assets/Prefabs/Player.prefab` 하드코딩이고, NPC 프리팹에는 `CharacterJoint`가 하나도 없다.
2. **NPC에 사망 개념이 없다.** HP 0이 `Stun`으로 간다 — "언제 래그돌에 들어가나"를 먼저 정해야 한다.
   (`BombDevice.ServerExplode`의 "NPC 폭발 피해는 아직 연결하지 않았다" 주석과 같은 매듭)

> **1. 폭발은 어차피 사망 연출이 맞다.** 본문은 "사망 래그돌은 이번 범위 밖"으로 적었지만, 실제 순서는 `폭발 데미지 → 사망 → 래그돌 → 넉백 임펄스`다. 래그돌 진입을 `IncapacitationCause.Die` 하나로 잡으면 폭발·진압봉·납치 린치가 전부 같은 경로를 타고, 폭발은 **임펄스가 붙는다는 점**만 다르다. 살아남은 사람은 지금의 슬라이드 넉백을 그대로 쓴다.
>
> **2. 지금 수치로는 폭발에 안 죽는다.** `m_explosionDamage = 60`, `m_maxHp = 100`이고 데미지에는 거리 감쇠가 없어 반경 8m 안이면 전원 균일하게 60이다. 그래서 **데미지에도 거리 감쇠를 넣는다** — 폭심은 즉사(래그돌), 가장자리는 생존(슬라이드 넉백). "가까운 놈은 날아가고 먼 놈은 밀린다"가 자동으로 나온다. 기준값 제안은 폭심 150 / 가장자리 비율 0.2 / 즉사 반경 ≈ 3.3m이고, GDD 365줄의 밸런스 ⚠ 항목과 함께 플레이테스트로 확정한다.
>
> ### 본문에서 확정된 항목
>
> - **카메라: (b) 3인칭.** 오너는 `OwnBody` 레이어 컬링 때문에 **자기 몸이 아예 안 보인다**(`m_ownBodyRoot`가 본이 아니라 스킨드 메시라서). 자기 몸이 날아가는 걸 보는 게 이 기능 재미의 절반이라 Die 동안만 메시를 Default로 되돌리고 카메라를 3인칭으로 뺀다. 머리 뼈에는 붙이지 않는다(멀미).
> - **콜라이더 레이어:** 신규 `Ragdoll` 레이어(슬롯 10) + 지형하고만 충돌. 본문이 걱정한 "오너만 레이어가 다르다"는 실제로는 없었다 — `SetLayerRecursively`가 메시만 덮고 뼈는 안 건드린다. 다만 뼈가 Default라 조준 레이에 걸리는 문제는 그대로라 전용 레이어는 필요하다.
> - **범위:** 1차는 **플레이어만**. NPC 래그돌(본문의 원래 범위)은 플레이어가 검증된 뒤 후속으로. NPC는 서버 `NavMeshAgent` Warp·`Stunned`/`Captured` 유지 타이밍·`NpcProneCollider`까지 얽혀 검증 표면이 훨씬 넓다.
>
> ### 완료 기준 (1차)
>
> - [ ] 플레이어 프리팹에 래그돌 구성, 폭발 사망 시 래그돌로 날아가고 착지 후 정착
> - [ ] 진압봉·린치 등 다른 사망 경로도 같은 래그돌로 무너짐
> - [ ] 반경 가장자리 생존자는 기존 슬라이드 넉백 유지
> - [ ] 래그돌 뼈 콜라이더가 조준 레이·상호작용 판정을 방해하지 않음
> - [ ] 정착 후 시각 몸통과 CharacterController가 어긋나지 않음 (운반 조준·본부 부활이 정상 동작)
> - [ ] 본부 부활 시 애니메이터로 부드럽게 복귀 (정착 포즈 → 기상 모션)
> - [ ] 멀티(호스트+클라 2인 이상)에서 각 피어가 래그돌을 보고, 정착 위치는 서로 일치
