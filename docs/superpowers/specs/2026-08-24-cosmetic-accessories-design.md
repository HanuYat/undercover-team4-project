# 치장 아이템 — 착용 외형 설계 (#818 A 슬라이스)

> 작성 2026-08-24. 수염·모자 등 치장 아이템을 **입고, 저장하고, 남의 화면에 보이게** 하는 부분.
> 토큰 경제·자판기 가챠·보유함 UI는 이 문서 범위 밖이다 (§8).

## 1. 왜 쪼갰는가

#818 본문은 사실상 독립적인 덩어리 넷을 담고 있다. 스펙 하나로 묶으면 각 부분이 엉성해지고 PR이 커진다.

| | 덩어리 | 의존 | 이 문서 |
|---|---|---|:---:|
| **A** | **착용 외형** — 부착점·카탈로그·계정 저장·서버 스폰 심기 | 없음 | ✅ |
| B | 토큰 경제 — 라운드 클리어 시 +1, 계정 귀속 | 없음 | ✕ |
| C | 자판기 가챠 — 상점 오브젝트, 서버 권위 뽑기, 중복 처리 | A + B | ✕ |
| D | 보유함·착용 선택 UI | A | ✕ |

**A를 먼저 하는 이유**: 위험이 여기 몰려 있다. 남의 화면·CCTV에서 첫 프레임부터 옳게 보여야 하고
(`PlayerCosmetics`가 #790에서 오너 쓰기 → 서버 쓰기로 갈아탄 이유가 그것이다), 에셋이 로봇 머리에
실제로 맞는지도 붙여 봐야 안다. B·C·D는 A가 없으면 눈으로 확인할 대상 자체가 없다.

## 2. 기존 색 경로를 그대로 미러링한다

로봇 색(#432·#790)이 이미 "계정 저장 → 명부 → 서버가 스폰 때 심기 → 전 피어가 그린다"를 완성해 뒀다.
치장은 **그 다섯 자리에 값을 하나 더 태우는 것**이고, 새 관례를 만들지 않는다.

| 자리 | 색 (기존) | 치장 (신규) |
|---|---|---|
| 값 보관 (로컬·동기 읽기) | [`GameSettings`](../../../Assets/Scripts/Core/GameSettings.cs) `Get/SetPlayerColor` · `OnPlayerColorChanged` | 같은 파일에 `Get/SetAccessory(EAccessorySlot)` · `OnAccessoryChanged` |
| 계정 저장 (Cloud Save) | [`CosmeticsSaveService`](../../../Assets/Scripts/Save/CosmeticsSaveService.cs) → `CosmeticsSaveData.Colors` | 같은 서비스·같은 키에 `Accessories` 추가 (§5) |
| 로비 UI | [`PlayerColorPanel`](../../../Assets/Scripts/UI/Panels/PlayerColorPanel.cs) | 같은 패널에 슬롯별 선택 추가 (§7) |
| 명부 전파 | [`LobbyPlayerEntry.Colors`](../../../Assets/Scripts/Scene/LobbyPlayerEntry.cs) | `LobbyPlayerEntry.Accessories` |
| 적용 | [`PlayerCosmetics`](../../../Assets/Scripts/Player/View/PlayerCosmetics.cs) (머티리얼 틴트) | **`PlayerAccessories`** (신규 — 자식 오브젝트) |

**`PlayerCosmetics`를 확장하지 않고 컴포넌트를 새로 두는 이유**는 메커니즘이 다르기 때문이다. 색은
`BodyTint`를 통한 머티리얼 조작이고 치장은 자식 오브젝트의 생성·파괴다. 게다가 `PlayerCosmetics`에는
"배정 전에는 남의 몸을 아예 그리지 않는다"(#790)는 미묘한 가드가 있어, 거기에 슬롯 배열까지 얹으면
`Apply()`가 두 관심사를 섞는다. 지금 166줄인데 더 키우면 팀 기준(250줄)에 걸린다.

## 3. 데이터 모델

```
EAccessorySlot { Headwear, FacialHair, Hair, Eyewear, Facewear, Earwear }  // 추가는 뒤에만
AccessorySet                                  // 슬롯별 byte. PlayerColorSet과 같은 모양
AccessoryCatalog : ScriptableObject           // 슬롯별 프리팹 배열
```

- `AccessoryCatalog`는 슬롯마다 프리팹 배열을 갖는다. **배열 인덱스가 곧 네트워크로 오가는 값**이다.
- **인덱스 0 = 안 씀.** 실제 아이템은 1번부터다. 카탈로그 0번 원소는 **비워 둔다(프리팹 참조 없음)** —
  0을 받으면 아무것도 붙이지 않으므로 그 자리는 조회되지 않는다.
- 수치·목록은 코드에 박지 않고 에셋으로 뺀다 (GDD 10-4).

**폭이 두 군데서 다른 것은 의도다.** 네트워크로 오가는 `AccessorySet`은 슬롯당 `byte`이고
(`PlayerColorSet`과 같은 모양 — 대역폭을 아낀다), 계정에 저장하는 `CosmeticsSaveData.Accessories`는
`int[]`다(기존 `Colors`와 같은 모양 — `JsonUtility` 직렬화가 단순하다). 슬롯당 아이템이 255종을
넘기면 그때 `byte`를 넓혀야 하고, 그 지점이 이 설계의 상한이다.

### 0을 "안 씀"으로 둔 것이 이 설계의 핵심이다

`PlayerCosmetics`는 "`PlayerColorSet`이 byte 인덱스라 미배정을 표현할 수 없다(0이 곧 첫 색이다)"는
이유로 `m_assigned`라는 별도 `NetworkVariable`을 두고, 배정 전에는 **남의 몸을 통째로 숨긴다**(#790).
치장은 기본값 0이 그 자체로 안전한 상태라 **그 가드가 통째로 필요 없다** — 값이 늦게 도착해도
"맨머리 → 모자"로 바뀔 뿐, 틀린 것을 확신 있게 그리는 순간이 없다.

## 4. 네트워크

`PlayerAccessories : NetworkBehaviour`, `NetworkVariable<AccessorySet>`
(Read `Everyone` / Write `Server`).

- **서버가 `OnNetworkSpawn`에서 명부(`SessionRoster.TryGetEntry`)를 읽어 심는다.** 여기서 쓴 값은
  스폰 페이로드에 실려 나가므로 남의 화면·CCTV에 **첫 프레임부터** 옳게 보인다. 오너 쓰기로는
  원리적으로 불가능한 일이다(오너는 스폰 메시지를 받은 뒤에야 쓴다) — #790에서 이미 겪었다.
- **오너 보고 RPC는 안전망으로만 유지한다.** 명부 보고가 스폰을 앞지르지 못한 경합(입장 직후 게임 씬
  직행)에서 한 박자 늦게 고쳐진다. 값이 같으면 `NetworkVariable`이 스스로 무시하므로 정상 경로에서
  대역폭을 먹지 않는다. 코스메틱이라 서버가 값을 검증하지 않는다(색과 같은 방침).

## 5. 계정 저장과 마이그레이션

`CosmeticsSaveData`에 `Accessories`(슬롯별 int 배열)를 추가하고 `k_version`을 1 → 2로 올린다.

> ⚠ **그냥 버전만 올리면 기존 사용자의 색이 날아간다.**
> `CosmeticsSaveService.ReadAsync`는 지금 버전이 다르면 **레코드를 통째로 무시**한다. 2로 올리는
> 순간 기존 계정의 저장된 색이 버려지고 기본색으로 돌아간다.

그래서 버전 검사를 **"다르면 무시" → "1이면 색만 읽고 치장은 기본값"** 으로 완화하는 마이그레이션
경로를 함께 넣는다. 2보다 큰(미래) 버전은 지금처럼 무시한다 — 모르는 포맷을 추측해 읽는 것보다
기본값이 낫다는 기존 판단은 그대로다.

저장 실패는 경고만 남기고 흐름을 막지 않는다 (`SaveService`·`CosmeticsSaveService`의 기존 방침).

## 6. 적용 — 어떻게 붙이나

`Player.prefab`은 Synty 휴머노이드 리그다. 부착 대상은 **3인칭 몸통 리그의 머리 본**이다:

```
Root/Hips/Spine_01/Spine_02/Spine_03/Neck/Head      ← 여기에 붙인다
Camera/FPArm_Right/Root/.../Head                    ← 1인칭 팔 리그. 붙이지 않는다
```

1인칭에 안 붙이는 것은 의도다 — FPS에서 자기 모자가 자기 화면에 보이지 않는 것이 자연스럽다.

- **런타임 `Instantiate`**로 붙인다. 프리팹에 전 아이템을 미리 넣고 토글하는 방식
  (`NpcCatalogAppearance`가 바디 20종에 쓰는 방식)은, 가챠로 아이템이 늘 때마다 `Player.prefab`을
  고쳐야 해서 머지 충돌을 계속 만든다. 런타임 부착이면 카탈로그 에셋만 늘리면 되고, 로비 미리보기·
  초상 같은 다른 자리에도 같은 카탈로그로 붙일 수 있다.
- 값이 바뀌면 해당 슬롯의 기존 인스턴스를 지우고 다시 만든다. 6명 × 6슬롯이라 비용은 무시할 수 있다.
- 부착물은 **`NetworkObject`가 아니다.** 각 피어가 복제된 인덱스를 보고 로컬로 만든다 — 코스메틱이라
  복제할 이유가 없다.

> ⚠ **부착물 프리팹에는 콜라이더를 넣지 않는다.** 넣으면 `PlayerInteractor`의 조준 레이,
> `NpcResistState`의 타격 `OverlapSphere`, 진압봉 판정에 걸려 "게임플레이에 영향 없음"이 깨진다.

## 7. 로비 UI (A의 경계)

`PlayerColorPanel` 옆에 슬롯별 선택을 붙인다. **보유 개념이 아직 없으므로 카탈로그의 전 아이템을
고를 수 있다** — 보유함 필터는 D에서 얹는다.

A만 끝나도 "모자 쓰고 게임 들어가기"가 완성돼, 이 슬라이스의 핵심 리스크(남의 화면에 첫 프레임부터
보이는가)를 사람이 눈으로 검증할 수 있다. 그게 UI를 여기까지 당겨 온 이유다.

## 8. 범위 밖 (후속 슬라이스)

- **B 토큰 경제** — 라운드 클리어 시 계정에 +1. `RoundManager`/정산 흐름에 훅.
- **C 자판기 가챠** — 상점 씬 설치물, 토큰 1개 소모, 서버 권위 뽑기, 중복 보상 처리.
- **D 보유함·착용 선택** — A의 로비 UI에 보유 필터를 얹고 보유 목록을 계정에 저장.
- **에셋 준비** — 외부 저장소에서 관리한다 (2026-08-24 확인). 이 문서는 에셋 조달을 다루지 않는다.

## 9. 검증

테스트 프레임워크 코드가 없는 프로젝트라 수동이다 (CLAUDE.md).

**핵심 확인 사항**
1. MPPM 2인 이상 — 로비에서 각자 다른 모자를 고르고 게임 씬 진입 → **남의 화면에 첫 프레임부터** 제 모자가 보인다 (기본 외형이 한 번 스쳤다가 바뀌면 실패다)
2. 본부 CCTV에서도 같게 보인다
3. 로그아웃 → 재접속 후에도 착용 상태가 유지된다

**회귀 지점**
- **기존 사용자의 색** — `k_version`을 올렸다. 이미 색을 저장해 둔 계정으로 로그인해 색이 그대로인지 볼 것 (§5의 마이그레이션이 실제로 도는지)
- **게임플레이 무영향** — 모자 쓴 플레이어를 조준·타격해 판정이 달라지지 않는지 (§6의 콜라이더 금지)

## 10. 알려진 위험

- ~~**에셋이 로봇 머리에 맞는지는 붙여 봐야 안다.**~~ 해소됐다 — Head 본 공간에서 재 보니 로봇 머리
  bounds가 max (0.11, 0.22, 0.14)로 Synty 인간 머리 (0.13, 0.22, 0.14)와 위·앞·뒤가 같다(좌우만
  0.02씩 좁다). 같은 리그라서다. 전 부착물을 오프셋 0·스케일 1로 붙였고 프리뷰 렌더로 확인했다.
- **슬롯 조합 충돌** — 슬롯이 여섯(모자·수염·머리카락·안경·마스크·귀)이라 겹치는 조합이 실제로 있다:
  전면 헬멧 + 마스크, 모자 + 머리카락(모자 메시에 머리카락이 딸린 것들), 마스크 + 수염. 지금은 다루지
  않는다 — 순수 코스메틱이라 겹쳐도 게임플레이가 깨지지 않고, 배타 규칙은 실제로 거슬리는 조합이
  모였을 때 카탈로그에 얹는 편이 낫다.
