## 1. 한 문장 요약

`partial` **12파일 1,978줄**(실코드 1,044)짜리 한 클래스를 **코어 1개 + 도메인 컴포넌트 9개**로 갈랐다.
`NpcController`는 실코드 **257줄**이 됐고, `partial`은 없앴다.

## 2. 이 문서가 남는 이유 — partial의 두 번째 반례

[PlayerEscorter 분리 §2](playerescorter-split.md#2-이-문서가-남는-이유--partial의-반례)가 "`partial`은 결합도를
줄이지 않는다"의 실증이었다면, 여기는 **"성장도 못 막는다"** 의 실증이다.

`NpcController`는 #259로 이미 도메인별 partial로 갈라져 있었다. 그런데도:

| 시점 | 구성 |
|---|---|
| #259 직후 | 11파일 1,573줄 |
| #513 (기상 예약) | 12파일 1,830줄 |
| #529·#522 (피격 연출·반출 재연행) | 12파일 **1,978줄** |

**2주 만에 +405줄이고 파일 수는 그대로다.** 새 도메인이 새 파일로 가니 본체는 안 자라는 것처럼 보였지만,
클래스는 한 덩어리라 어디든 붙었다. 경계가 없으면 성장을 셀 수만 있고 막을 수는 없다.

이전 계획서는 컴포넌트 분리를 비추천했다 — *"프리팹 수정 + 상태 클래스의 참조 경로 변경이 필요해서
'이동만' 리팩토링이 아니게 된다"*. **"이동만"이 목표였을 때는 옳았고** 그 목표는 달성됐다. 실측해 보니
경로 변경은 작았다: 상태 클래스의 `m_owner.*` 참조 **285건 중 76건**만 바뀐다(나머지 209건은
`Agent`·`transform`·`name`·`StateMachine`처럼 코어에 남는 것들이다).

## 3. 분리 규약 6개 — 10번째 부품이 생기면 그대로 쓴다

파일럿(#540)에서 4개를 확정하고 이후 PR이 둘을 보탰다. **여섯 개 전부 실제 코드로 사례가 있다.**

1. **컴포넌트 접근자는 둔다, 값 위임은 두지 않는다.**
   O: `public NpcRopeDrag Rope => m_rope;` → 호출부는 `npc.Rope.IsRoped`
   X: `public bool IsRoped => m_rope.IsRoped;` — 줄 수만 옮긴 partial과 같아진다.
   접근자가 필요한 이유는 부품이 `m_owner`만 들고 있어서다(없으면 매 틱 `GetComponent`).
2. **부품에 `Update`/`FixedUpdate`를 만들지 않는다.** 코어가 `Tick()`을 정해진 순서로 부르고 게이트 조건도
   코어가 부품에 묻는다 — `if (m_knockback.IsKnockedBack) { m_knockback.Tick(); return; }`. 근거는 §4.
3. **튜닝 SO는 코어가 계속 들고, 부품이 코어의 `internal` 프로퍼티로 읽는다.** 부품이 `[SerializeField]`로
   따로 받으면 배선이 프리팹 4개 × 부품 수만큼 늘어난다. 부품은 같은 어셈블리(`Assembly-CSharp`,
   `Assets/Scripts`에 asmdef 없음)라 `public`까지 열 필요가 없다. 지금 5개가 열려 있다.
4. **부품은 `NetworkBehaviour`, `[RequireComponent]`는 코어 → 부품 한 방향만.** 양방향은 순환 의존이라
   둘 중 하나만 떼는 것이 막힌다. `ShopStand.cs:23`이 같은 구조다.
5. **부품은 프리팹에 명시 저장한다 — 자동 생성에 기대지 않는다.** `[RequireComponent]`는 이미 배선된
   프리팹에도 소급 적용되지만 **그 결과가 에셋에 저장되지 않는다.** 자세한 것은 §6.
6. **도메인 PR은 "제 집 정리" 선행 커밋으로 시작한다.** 파일 경계와 도메인 경계가 어긋난 곳을 먼저
   바로잡는다. 두 종류다:
   - **남의 도메인 멤버** → 제 집으로. (`ReleaseFromCustody`가 `Intrude.cs`에 있던 것 — 1건뿐이었다)
   - **도메인 멤버가 아닌 공용 헬퍼** → 코어로 승격. 부품에 딸려 보내면 "Custody가 Rope를 참조한다"는
     **가짜 의존**이 생긴다. (`TryWarpNear`·`SweepHitsObstacle` 2건)

   **점검은 매번 하되 선행 커밋이 늘 생기지는 않는다** — 3·5·6번은 없어 그냥 갔다. 파일럿과 모양이
   달라 리뷰어가 의아해하므로, 없으면 "점검했고 없었다"를 PR 본문에 적는다.

## 4. 불변식 셋 — 깨져도 컴파일은 되는 것들

### 4-1. `Update` 게이트 순서가 사양이다

```
TickNavMeshRecovery() → 밧줄 → 기상 대기 → 넉백 게이트 → 스턴 게이트 → FSM Tick
```

- NavMesh 회수는 **전부보다 먼저** — 뒤로 내리면 스턴 게이트에 가려 기절한 채 굳은 NPC에 영영 닿지 못한다 (#557)
- 밧줄은 게이트보다 **먼저** — 묶인 채 기절한 대상은 스턴 오버레이를 단 채 끌려가야 한다 (#390)
- 기상 대기도 게이트보다 **먼저** — 일어나는 도중 기절·넉백을 맞은 대상의 예약이 영원히 남는다 (#513)
- 스턴은 넉백 **뒤** — 둘이 겹치면 넉백이 이긴다 (#292)

**단계가 늘어난다는 것 자체가 이 불변식의 근거다** — 착수 후에도 #557이 하나 늘렸다. 부품이 각자
`Update`를 가지면 이 순서가 Unity의 컴포넌트 실행 순서에 위임된다. **조용히 깨지는 종류의 회귀**다.

### 4-2. `OnDamaged`는 HP 반영 *직전* 발행이 계약이다 (#371)

구독자(납치 이벤트)가 상태를 바꿀 수 있어야 하고(임무 해제 → 배회) 그 다음에 기절 전이가 얹혀야 한다.
뒤로 옮기면 넉백 기절로 바뀐 상태를 임무 해제가 덮어써 **기절이 조용히 취소**된다.

### 4-3. NetworkVariable 도착 순서를 새로 신뢰하지 않는다

동기화 값이 컴포넌트별로 갈리면 원격 피어의 도착 순서 보장이 더 약해진다. #462 착석 폴링과 #369 끌림
폴링이 이미 그 전제로 짜여 있다(상태 훅 대신 폴링).

## 5. 절단면 — 왜 도메인 9개인가

**"상태머신이라 못 뺀다"는 진단이 아니었다.** FSM은 이미 `NpcStateMachine` + `States/*`(13개)로 분리돼
있었고, 컨트롤러는 상태들이 읽는 **데이터·API 허브**였다. 그래서 절단면은 FSM이 아니라 도메인이다.

**다만 도메인은 FSM 상태와 1:1이 아니다.** `Captured` 하나에 Rope·StandUp·Custody가 함께 얹혀 있다 —
**"상태 하나씩" 빼는 것은 불가능**했다.

| 컴포넌트 | 도메인 | NetworkVariable / RPC |
|---|---|---|
| `NpcCustody` | 연행 · 인계 표식 · 수감(순간이동) · 감옥 퇴장 · 반출 표식 | `m_jailExtractedSynced` |
| `NpcHealth` | 체력 + `IDamageable` + `OnDamaged` | `m_syncedHp` · `PlayDamagedRpc` |
| `NpcIntruder` | 침입 | — |
| `NpcKnockback` | 넉백 비행 | — |
| `NpcPenaltyAgent` | 오검거 · 납치 페널티 | `m_abductionDuty` |
| `NpcReaction` | 도주 · 저항 · 스윙 | 스윙 `ClientRpc` |
| `NpcRopeDrag` | 밧줄 끌기 · 무게 · 테더 | 동기화 3개 |
| `NpcStandUp` | 기상 예약 · 재포획 창 | `m_standUpPendingSynced` |
| `NpcStun` | 스턴 오버레이 | `m_syncedStunned` · `TaserStunStartedRpc` |
| `NpcController` (코어) | NavMeshAgent · FSM 구축·틱 · 상태 동기화 · `Update` 게이트 · `SetFrozen` · 순간 이벤트 중계 · config SO 보관 · 공용 헬퍼 | `m_networkState` |

**`NpcStandUp`이 별 부품인 이유**: 기상 예약을 밧줄 풀림(#513)과 기절 기상(#269) **두 도메인이 공유**한다.
어느 한쪽에 넣으면 다른 쪽이 그 내부 상태를 만지게 된다. 같은 이유로 `RaiseStandUp` 순간 이벤트는
**코어 중계로 남겼다** — 부품 → 부품 의존이 새로 생기지 않고, 구독자(`NpcAnimationDriver`) 경로도 안 바뀐다.

**양방향 쌍은 한 PR로 묶었다.** 한쪽만 먼저 빼면 "A→B는 컴포넌트 참조, B→A는 여전히 코어 내부 호출"인
어정쩡한 중간 상태가 남는다. 그래서 무력화 클러스터는 `NpcHealth`+`NpcStun`(#563),
`NpcRopeDrag`+`NpcStandUp`+`NpcKnockback`(#570)으로 갔다. **중간 상태는 한 번도 생기지 않았다.**

**빼지 않고 지운 것 하나** — `Holding`(임시 거처, 31줄)은 **도달 불가 코드였다.** `60f42aa`(#310)가 호출부·
구독을 전부 지웠는데 컨트롤러 API와 FSM 상태만 고아로 남아 있었다. 뽑았으면 **죽은 `NetworkBehaviour`를
프리팹 4개에 붙일 뻔했다.** 도메인 PR을 시작하기 전에 "이 도메인이 아직 살아 있는가"부터 볼 것.

## 6. Unity·NGO에서 실제로 문 것

이 절이 다음 컴포넌트 분리에 가장 쓸모 있다.

**① `[RequireComponent]`의 소급 적용은 에셋에 저장되지 않는다.**
파일럿 임포트 로그에 `Creating missing NpcIntruder component for NpcController in ...` × 4가 찍히지만
**프리팹 파일은 그대로다.** 저장소가 실제 구성을 기록하지 못하고, `[RequireComponent]`를 떼면 조용히
사라지며, 무엇보다 **직렬화 필드를 가진 부품은 임포트마다 인스펙터 값이 초기값으로 돌아간다.**
→ 인스펙터에서 부품을 한 번 껐다 켠 뒤 저장한다(그냥 열고 저장만 하면 dirty가 안 잡힌다).

**② NetworkBehaviour 인덱스는 프리팹의 컴포넌트 구성 순서로 정해진다.** `NetworkVariable`이나 RPC를 든
부품은 ①이 더 중요하다 — 에셋에 기록되지 않은 구성은 피어 간 매칭의 근거가 없다.

**③ 인덱스 문제는 호스트 화면에서 안 보인다.** 갈아탄 `NetworkVariable`이 클라 표현·계산용이면 호스트는
진실값을 쓰므로 멀쩡해 보인다. **Play 회귀는 원격 클라 화면을 보면서 돌릴 것.**

**④ 프리팹을 저장하면 통째로 재직렬화되어 부품 추가 외의 변경이 딸려 온다.** 두 종류가 나왔다:
- 그동안 기록된 적 없던 필드가 기본값으로 쓰인다 → **코드 기본값과 대조할 것.** 다르면 인스펙터에서
  조정한 값이 덮인 것이다.
- 코드에서 지워진 필드의 잔재가 함께 정리된다(`NpcAnimationDriver.m_sitBeginSeconds`). 무해하지만
  **지워진 필드인지 아직 쓰이는 필드인지 grep으로 가를 것** — 후자면 인스펙터 값이 날아간 것이다.

`GlobalObjectIdHash`는 7개 PR 내내 한 번도 안 바뀌었다.

**⑤ 한 파일을 짧은 간격으로 두 번 쓰면 Unity가 임포트를 놓칠 수 있다.** `NpcRopeDrag.cs`가 `.cs`인데도
스크립트가 아닌 임포터로 물려 컴파일 소스 목록에서 빠졌다. 증상은 "방금 만든 부품 타입을 못 찾는다"는
**CS0246**이다. **리프레시·`.meta` 삭제로는 안 풀리고 에디터 재시작으로 풀렸다.**
→ 코드를 의심하기 전에 Editor.log의 `Start importing … Importer(<id>)`를 다른 `.cs`와 대조할 것.

**⑥ Editor.log로 컴파일을 판정할 때 에러 건수만 세면 오판한다.** 로그는 append-only이고, 파일을 여러 개
고친 뒤 에디터를 열면 첫 리프레시가 일부만 집어 실패했다가 다음 리프레시가 성공하는 일이 정상적으로
일어난다. 마지막 `CopyFiles Library/ScriptAssemblies/Assembly-CSharp.dll` **뒤에** 에러가 있는지로 판정한다.

**⑦ 프리팹은 모든 분리 PR의 공통 충돌면이다.** 스크립트가 안 겹쳐도 프리팹에서 만난다. YAML 충돌이 나면
머지하지 말고 **에디터에서 다시 배선**하는 쪽이 빠르고 안전하다.

## 7. 검증 절차 — 다음 분리에서도 그대로 쓴다

1. **컴포넌트 누락** — `grep -rl <부품 guid> Assets --include=*.prefab`으로 프리팹 4개에 실제로 들어갔는지.
   `[RequireComponent]`의 소급 적용을 믿지 않는다(§6-①).
2. **멤버 유실** — 분리 전 시그니처 목록과 분리 후 합본을 `comm -23`으로 대조. **주석 압축을 같은 PR에
   담았다면 눈으로 하지 말 것** — diff에서 '옮긴 것'과 '지운 것'이 섞인다.
3. **컴파일** — Unity Console 에러 0. Editor.log로 볼 때는 §6-⑥.
4. **Play 회귀 (MPPM 2인 이상, Apocalypse 맵)** — **전부 돌릴 필요는 없다.** 순수 이동이라 위험은
   ① 프리팹 배선 누락(NRE) ② `NetworkVariable`/RPC 인덱스 ③ 그 PR에서 *쓰기 방향*이 바뀐 경로에 몰린다.
   그 셋에 걸리는 항목만 고르고, **남긴 항목은 PR 본문 "후속으로 미룬 것"에 이유와 함께 적는다**
   (자동 리뷰가 누락으로 잡지 않게 하는 관례이기도 하다). 실제로 PR당 4~5개를 돌렸다.
5. **인스펙터 튜닝값** — SO를 코어에 남기므로(규약 3) 값 자체는 안 움직인다. 참조가 살아 있는지만 본다.

**동작이 바뀐 것 2건** — 나머지는 전부 순수 이동이다.

  도메인 코드를 **처음으로 한자리에 모아 놓고 읽자** 기존 결함이 드러났다.

  팀 확인 후 이슈는 닫혔다(2026-08-09).**
