## 0. 한 줄 — 원인

**권위 피어의 프레임레이트가 물리 스텝 레이트(50Hz)보다 높으면 걸린다.**

시체의 루트 추종(`TickCapsuleFollow` / `TickRootFollow`)이 **프레임마다** 뼈 리지드바디의
트랜스폼에 쓰는데, 물리는 50Hz로만 돈다. 스텝당 주입 횟수가 1을 넘으면 솔버가 관절 오차를
못 따라잡고, 몸은 안 내려가면서 뼈만 떤다.

- **60fps 호스트 → 스텝당 1.2회 주입 → 정상**
- **100fps 호스트 → 스텝당 2.0회 주입 → 슬로모션**

관측자의 fps는 무관하다. **호스트(권위)의 fps만 관계있다.**

**수정은 들어갔다**(`95ed43ac`) — 컴파일만 확인했고 **Play 미검증**이다.

### 이어받는 세션이 처음 할 일

1. **§7을 먼저 본다** — 프리팹·워킹트리 상태와, 아직 판단이 안 된 변경 두 가지
2. **100fps 호스트로 빌드해 재측정** — 그것이 고장 나던 조건이다
3. **§6 판정표대로 `권한=True` 줄만 본다** — 관절오차 수렴 / 뼈속도 잦아듦 /
   골반낙차 0.4~0.7m / 최고하강 1.8~2.1m/s
4. 통과하면 §3-2 → 계측 전체 제거. 실패하면 §3-1의 트레이드오프부터 의심

⚠ **§4를 읽지 않고 옛 가설로 되돌아가지 말 것.** 1·2판이 짚었던 `침투해소상한` ·
speculative CCD · 밧줄 스프링은 전부 근거와 함께 배제됐다.

## 2. 원인 — 실측

### 2-1. 호스트의 프레임레이트가 갈랐다

`vSync=1 · 상한=-1`이라 fps는 모니터 주사율을 그대로 따라간다.

| 머신 | 주사율 | 실측 fps | **호스트일 때** |
|---|---|---|---|
| **Player1** (8bPe) | **60.0Hz** | **60.3** | ✅ **정상** |
| **Player2** (njXg2) | 100.0Hz | 100.0~100.3 | ⚠ **슬로모션** |
| **Player3** (MLU20) | 100.0Hz | 100.3 | ⚠ **슬로모션** |

**관측자 fps는 무관하다** — 교차 대조가 양방향으로 성립한다:

- Player1은 **60.3fps인데** 100fps 호스트 방에서 슬로모션을 봤다 (골반낙차 0.24 / 0.25 / 0.22m)
- Player3은 **100.3fps인데** 60fps 호스트 방에서 정상을 봤다 (골반낙차 0.49~0.73m)

1판 로그의 아픈 세션도 호스트가 Player2였다 → **60fps 호스트 1대 정상 / 100fps 호스트 2대 재현.**

### 2-2. 권위측 지표 (권한=True)

| | 골반낙차 | 최고하강 | 관절오차곡선 | 뼈속도곡선 |
|---|---|---|---|---|
| **60fps 호스트** ×5 | 0.39~0.72m | **1.86~2.04 m/s** | 초반 22~33mm → **3.6~15mm로 수렴** | 0.4~1.8 → **0.01~0.5로 잦아듦** |
| **100fps 호스트** ×3 | **0.22~0.25m** | **0.28~0.73 m/s** | 12~80mm를 **오가며 수렴 안 함** | **1.79~7.20으로 끝까지 높음** |

`관절오차곡선` 원자료:

```
정상  #9 [12.85 8.48 12.35 3.63 3.63]   #8 [33.05 12.25 12.53 28.25 15.46]
      #7 [26.48 11.69 11.77 8.47 23.14] #9 [32.02 7.94 5.05 5.03 27.31]
슬로모 #10 [28.72 15.00 70.68 29.61 12.51] #9 [25.60 16.20 22.99 56.43 46.17]
      #8 [59.75 45.55 31.16 55.96 69.68]  ← 3초 뒤에 오히려 커진다
```

**정상은 수렴하고, 슬로모는 수렴하지 않는다.** 그동안 "몸이 안 내려간다"고 본 것은
솔버가 매 스텝 중력이 아니라 이 오차를 푸느라 낙하에 쓸 예산이 없었던 것이다.

### 2-3. 메커니즘

`Fixed Timestep = 0.02`(50Hz)인데, 루트 추종은 **프레임마다** 돈다:

| 어디 | 무엇을 |
|---|---|
| [PlayerRagdoll.cs:784](../Assets/Scripts/Player/View/PlayerRagdoll.cs:784) | `Update()` → `TickCapsuleFollow()` (권위 전용) |
| [PlayerRagdoll.cs:1735](../Assets/Scripts/Player/View/PlayerRagdoll.cs:1735) | `CapturePose()` → 루트 이동·회전 → `RestoreCapturedPose()` |
| [NpcRagdoll.cs:173](../Assets/Scripts/NPC/View/NpcRagdoll.cs:173) | `Update()` → `TickRootFollow()` — **같은 구조, 같은 버그** |

`RestoreCapturedPose()`는 뼈 11개에 `transform.SetPositionAndRotation`을 쓴다.

주석은 이것을 *"렌더 전용 — `m_AutoSyncTransforms = 0`이라 액터로 안 넘어간다"* 로 정당화하는데,
**그 전제가 틀렸다.** `autoSyncTransforms`가 0이어도 트랜스폼 쓰기는 **다음 시뮬레이션 스텝
직전에 PhysX로 flush된다** — 그 설정이 미루는 것은 *쿼리*(레이캐스트 등)가 보는 시점이지
시뮬레이션이 보는 시점이 아니다. 그리고 동적 바디의 트랜스폼에 쓰는 것은 PhysX에게
**텔레포트**여서 누적된 솔버·접촉 상태를 무효화한다.

왕복이 비트 단위로 정확하면 델타가 0이라 무해하지만, 잔차는 매 프레임 재주입된다:

| 호스트 fps | 스텝당 주입 | 결과 |
|---|---|---|
| 60 | 60/50 = **1.2회** | 솔버가 따라잡는다 → 오차 수렴 ✅ |
| 100 | 100/50 = **2.0회** | 솔버가 절반의 기회만 → 오차 발산 ❌ |

그리고 이 오차를 흡수할 장치가 하나도 없다 — 전 프리팹이
`AutoConfigureConnectedAnchor = 1` · `EnablePreprocessing = 0` · `EnableProjection = 0`이다(§4-B).

## 3. 고친 것

### 3-1. 본 수정 — 루트 추종을 물리 레이트에 묶었다 ✅ (컴파일 확인, **Play 미검증**)

`TickCapsuleFollow` / `TickRootFollow`를 **`FixedUpdate`로 옮겼다.** 주입이 스텝당 항상 1회가 되어
**프레임레이트와 무관**해진다 — 144Hz 호스트가 들어와도 같다.

잃는 것이 없다 — 뼈는 `Interpolate = None`이라 어차피 50Hz로만 갱신되고, 루트가 따라가는 대상인
골반도 50Hz로만 움직인다. 루트만 100Hz로 도는 것이 애초에 의미가 없었다.

| 파일 | 변경 |
|---|---|
| `PlayerRagdoll.cs` | `Update`에서 `TickCapsuleFollow()` 제거 → 새 `FixedUpdate`로 (게이트: `Ragdoll` + `HasMoveAuthority`) |
| `PlayerRagdoll.cs` | `FollowBodyYaw()`의 `Time.deltaTime` → **`Time.fixedDeltaTime`** (지수 감쇠라 시간 기준이 바뀌면 감쇠 속도가 바뀐다) |
| `NpcRagdoll.cs` | `Update`에서 `TickRootFollow()` 제거 → 새 `FixedUpdate`로 (게이트에 `!m_settled` 포함 — 잠든 몸 건너뛰기를 유지) |
| `RagdollPoseStreamer.cs` | **`[DefaultExecutionOrder(100)]`** |

⚠ **스트리머 순서를 왜 박았나.** 루트 추종이 `FixedUpdate`로 내려오면서 스트리머의 자세 캡처와
**같은 페이즈**가 됐다. `MonoManager.asset`이 없어 순서가 미지정인데, **루트 회전이 뼈의 로컬 값을
바꾸고 스트리머가 보내는 것이 바로 그 로컬**이라 어느 쪽이 먼저 도느냐로 보내는 자세가 갈린다.
뒤로 박아 **이번 스텝의 루트**를 기준으로 뜨게 했다. (이번 버그와 같은 계열의 함정이라 미루지 않았다)

**남는 트레이드오프:** `FixedUpdate`는 스텝 *앞*이라 루트가 **직전 스텝의 골반**을 읽는다 —
20ms, 3m/s면 6cm. 루트는 NetworkTransform이 100ms로 보간하는 대리값이라 무시할 수준으로 봤다.
재측정에서 원격의 위치 뒤처짐이 보이면 여기를 의심할 것.

### 3-2. 같이 볼 것 (본 수정 뒤 재측정)

- **`RestoreCapturedPose`의 "렌더 전용" 주석을 고친다** — 전제가 틀렸다(§2-3). 이 주석을 믿고
  같은 패턴을 다른 데 심으면 같은 버그가 난다
- `AutoConfigureConnectedAnchor`를 끄고 앵커를 바인드 기준으로 한 번만 굽는다 — 진입 오차가
  40~85mm나 되는 것이 정상은 아니다(§4-A). 본 수정으로 증상이 사라져도 이 값은 남는다
- `EnablePreprocessing`을 켜 본다 — 공짜고, 오차 흡수력이 달라진다

### 3-3. 하지 말 것

- **프레임레이트를 물리 레이트에 맞춰 묶는 것**(`vSyncCount = 2` 등) — 증상은 사라지지만
  게임 전체를 50fps로 내리는 대가다. 원인은 fps가 높은 것이 아니라 **프레임에 물리를 쓰는 것**이다
- **`Fixed Timestep`을 0.01로 올리는 것** — 100fps는 구제되지만 144Hz에서 다시 깨지고
  물리 비용만 2배가 된다

## 5. 별건으로 남는 회귀 — 캡슐 무시 재적용

`PlayerRagdoll.cs`의 `IgnoreOwnCapsule` 주석은 *"세 곳에서 다시 건다: 시체를 켜는 순간, 뼈를
다시 물리로 놓아줄 때, 캡슐이 꺼졌다 켜진 것이 관측될 때(Update)"* 라고 하는데:

- "뼈를 다시 물리로 놓아줄 때" → `a17b845d`에서 **삭제됨**
- "시체를 켜는 순간" → **B-2에서 시체 오브젝트가 없어져 소멸**

남은 것은 `Awake` · Update 폴러 · `PlayerRagdoll.SetControllerEnabled(true)` 셋뿐이고,
`PlayerTowedMotion`은 재적용이 **없는** `PlayerMovement.SetControllerEnabled`를 쓴다.
**주석이 스테일하고 방어가 두 칸 비었다** — 이 브랜치가 만든 회귀다. 슬로모션과는 무관하지만
고쳐야 한다.

## 6. 계측 사용법 (원인이 닫히면 전부 지운다)

플래그는 `Player.prefab`에 켜 둔 상태다(`m_logFallRate` · `m_logRopePull`).

| 태그 | 어디서 | 무엇을 |
|---|---|---|
| `[리그물리]` | 사망 1회 | 질량·감쇠·중력·침투해소상한·솔버 · `충돌검출` · `자동앵커` · `진입관절오차` |
| `[낙하속도]` | 사망 후 3초 창 | `비율` · `평균fps` · **`낙하곡선`** · `최고하강` · **`관절오차곡선`** · **`뼈속도곡선`** |
| `[밧줄]` / `[밧줄추적]` | 견인 시작 / 1.5초 뒤 | `관절` · `끌림` · `견인곡선` · `최고속도` · `평균속도` |
| `[자세도착]` | **원격 전용**, 2초 창 | 패킷/유실/`재생배율`/`홀드` |
| `[래그돌대역폭]` | 권위, 2초 창 | 패킷 · Hz · 페이로드B · 초당KB |
| `[소유권]` | 서버, 사망/부활 | `오너 X→Y` · `플레이어오브젝트유지` |

### 판정 기준 (3판에서 확정)

| 보는 값 | 정상 | 고장 |
|---|---|---|
| **`평균=…fps`** (권위 로그) | 물리 50Hz에 가까움 | **50Hz의 2배 근처** ← 근본 원인 |
| **`관절오차곡선`** | 수렴한다 (→ 한 자리 mm) | **수렴하지 않는다** |
| **`뼈속도곡선`** | 끝에서 0에 가까워진다 | **끝까지 높다** |
| `골반낙차` | 0.4~0.7m | **0.2~0.25m** |
| `최고하강` | 1.8~2.1 m/s | **0.3~0.7 m/s** |
