# PR 자동 리뷰 (Project Undercover)

PR 번호를 받아 아래 절차대로 리뷰하고, 리뷰어가 훑어보기 좋은 한국어 리포트를 출력한다.
`--comment` 플래그가 있으면 마지막에 리포트를 GitHub PR 코멘트로 게시한다(게시 전 사용자에게 확인).

인자가 없으면 현재 브랜치의 열린 PR을 `gh pr view --json number`로 찾는다. 그것도 없으면 사용자에게 PR 번호를 묻는다.

## 0. 사전 확인

1. `git status`로 워킹 트리가 깨끗한지 확인. 커밋 안 된 변경이 있으면 **중단하고** 사용자에게 알린다 (PR 체크아웃이 필요하므로).
2. PR 정보 수집:
   - `gh pr view <n> --json title,body,author,baseRefName,headRefName,files,mergeStateStatus`
   - `gh pr diff <n> --name-only` — 변경 파일 목록
   - **mergeStateStatus 확인**: `DIRTY`(base와 충돌)면 결론을 "충돌 해소 필요"로 하고 리포트 최상단에 표기. `BEHIND`(base보다 뒤처짐)면 경고 — 특히 씬 파일이 포함된 PR이 뒤처져 있으면 먼저 머지된 씬 작업을 덮어쓸 위험이 크다고 명시할 것.
3. **리뷰 대상은 `.cs` 스크립트 파일이 기본이다 (토큰 절약 — 팀 확정).**
   - 씬(`.unity`)·애니메이션(`.controller`/`.anim`/블렌드 트리)·`.asset`·`.meta` 등 비스크립트 파일은 diff가 몇 줄이든 **어떤 이유로도 내용을 읽지 않는다.** 변경된 파일의 **경로 목록만** 리포트에 기재해 리뷰어가 Editor에서 직접 확인하도록 안내한다.
   - **프리팹(`.prefab`)만 예외 — diff가 150줄 이하일 때만 읽는다** (`git diff --stat`으로 먼저 줄 수 확인). 프리팹 diff는 작으면서 배선 버그(잘못된 컴포넌트 참조, 씬 오브젝트 칸에 에셋 연결 등) 밀도가 높다 — PR #89에서 m_handsModel에 프리팹 에셋이 잘못 연결된 실사례를 잡음. 150줄 초과 프리팹은 다른 비스크립트와 동일하게 목록만 기재한다. 읽은 프리팹은 "리뷰 제외된 파일"이 아니라 검토 대상으로 리포트에 표기.
   - 단, 씬/프리팹에서 **삭제된 오브젝트 이름만** 경량 추출한다 (diff 전체를 읽지 말 것):
     `git diff origin/<base브랜치>...HEAD -- '*.unity' '*.prefab' | grep '^-.*m_Name:'`
     삭제된 이름 목록을 리포트에 기재하고, 기존 시스템의 진입점으로 보이는 오브젝트(매니저·어사이너류)가 삭제됐으면 **의도인지 확인 필요**로 경고한다. (PR #86에서 AppearanceAssigner가 씬 충돌로 삭제된 실사례의 재발 방지 장치)
   - `.cs` diff는 브랜치 체크아웃 후 `git diff origin/<base브랜치>...HEAD -- '*.cs'`로 얻는다.
   - 예외: `Assets/Imported/Synty/` 아래 파일이 변경 목록에 있으면 내용과 무관하게 **그 자체가 지적 사항**이다 (서드파티 에셋 수정 금지 — CLAUDE.md).

## 1. 컴파일 확인

1. 원래 브랜치명을 기억해 두고 `gh pr checkout <n>`으로 PR 브랜치 체크아웃.
2. **Unity MCP가 연결된 경우** (`mcp__UnityMCP__*` 도구 사용 가능):
   - `refresh_unity`로 에셋 리프레시 후, `editor_state` 리소스의 `isCompiling`이 false가 될 때까지 폴링.
   - `read_console`로 에러/워닝 확인. **컴파일 에러가 있으면 리포트 최상단에 표기** — 이 경우 이후 검사는 계속하되 결론은 "머지 불가"로.
3. **Unity MCP가 없는 경우**: 컴파일 검사를 건너뛰었다고 리포트에 명시하고, 대신 diff를 정적으로 훑어 명백한 문제(존재하지 않는 타입 참조, using 누락, 시그니처 불일치, 삭제된 멤버를 다른 파일이 참조)를 찾는다. 변경된 클래스/메서드명으로 `Grep`을 돌려 참조가 깨진 곳이 없는지 확인한다.
4. 리뷰가 끝나면 **반드시 원래 브랜치로 복귀** (`git checkout <원래 브랜치>`). 에러로 중단되는 경우에도 복귀할 것.

## 2. GDD 정합성 검사

`docs/GDD.md`가 게임 규칙의 정본이다. 변경 코드가 다루는 시스템에 해당하는 GDD 섹션을 **반드시 읽고** 규칙·로직·용어가 일치하는지 대조한다.

| 변경 코드의 주제 | 대조할 GDD 섹션 |
|---|---|
| 라운드/게임 흐름 | 3장 (게임 루프) |
| 본부·현장 역할, 통신 | 4장 |
| 조사/스캔/배터리/증거/판독 | 5장 (특히 5-2 배터리, 5-3 데이터 스키마) |
| NPC·용의자·시민·이벤트 | 6장 |
| 검거/오검거/전투/HP·다운 | 7장 |
| 아이템/인벤토리 | 8장 |
| 보상/자금/게임오버 | 9장 |
| 상태 enum 이름·값 | 10-2 |
| 몽타주/외형 | 10-3 |
| ScriptableObject 데이터 구조 | 5-3, 10-4 |

검사 요령:
- **수치는 대조하지 않는다.** HP, 속도, 배터리량, 페널티 금액, 타이머 같은 밸런싱 수치는 추후 조정되는 값이므로 GDD와 달라도 지적하지 않는다. 보는 것은 **규칙·로직·용어의 불일치**다 (예: 검거 판정 절차가 다름, 상태 전이가 GDD와 다름, GDD에 없는 개념 도입).
- enum 값/상태 이름이 GDD 10-2와 일치하는지 확인.
- 대조하려는 섹션 헤더에 `(초안 — 팀 검토 필요)`가 붙어 있으면 불일치를 "오류"가 아닌 **"초안과 다름 — 팀 확인 필요"** 로 분류한다.
- 기획 자료 간 모순이 의심되면 GDD **부록 B**(문서 통합 근거)를 최종 기준으로 삼는다.
- 데이터성 값(프로필, 스탯 등)이 ScriptableObject가 아니라 코드에 하드코딩되어 있으면 지적한다 (GDD 10-4).

## 3. 컨벤션 & 아키텍처 체크

1. **아키텍처 규칙** (`docs/architecture.md`가 정본 — 반드시 읽고 대조): **이 PR의 diff에 대해서만** R1~R8 위반을 찾는다. 기계적 검사 요령:
   - diff에 `FindFirstObjectByType` **추가**가 있으면 → 대상 타입이 App 등록 타입인지 확인(R1 위반), 아니면 architecture.md §4 예외 표에 기재됐는지 확인(미기재면 지적)
   - diff에 `static` + `Instance` 프로퍼티/필드 **신설**이 있으면 → R2 위반
   - diff에 `SceneManager.LoadScene` 직접 호출 **추가**가 있으면 → R7 위반 (AppHelper 내부 제외)
   - 새 매니저 클래스(베이스 상속)가 생겼으면 → App 필드/프로퍼티 추가·`[DefaultExecutionOrder]` 명시 여부(R4), `Awake`/`OnDestroy`의 `base` 호출(R5), 다른 매니저 구독이 Start에 있는지(R6), R3 등록 기준(유일성+교차 도메인 2곳 이상) 충족 근거
   - 매니저를 **필드에 캐싱**하는 코드가 추가됐으면 → R8 위반 (`private X Xxx => App.그룹.X;` 프로퍼티 패턴 안내)
   - 유예 조항(§5): 머지 이전에 열린 브랜치의 위반은 🟡로, 이후 신규 코드는 🟠 이상으로 분류
2. **네이밍 컨벤션** (CLAUDE.md / GDD 10-5): 신규·수정 코드에서 `m_`(private 인스턴스), `s_`(static), `k_`(const), `I`/`T` 접두사, 이벤트 `On` 접두사, public 멤버 PascalCase 위반을 찾는다.
3. **Netcode**: `NetworkBehaviour` 상속 코드가 변경됐다면 —
   - 서버 권한이 필요한 로직(판정·스폰·상태 변경)이 클라이언트에서 실행되지 않는지
   - `NetworkVariable` 쓰기가 서버/오너 권한과 맞는지, RPC 방향(`ServerRpc`/`ClientRpc`)이 적절한지
   - 새 네트워크 프리팹이 생겼다면 `Assets/DefaultNetworkPrefabs.asset` 등록 여부 (파일 변경 **목록**으로만 판단 — 내용은 읽지 않는다)
4. **일반 버그**: null 체크 누락, 이벤트 구독 해제 누락(OnDestroy/OnNetworkDespawn), Update 내 비싼 호출(GetComponent, Find 등), UniTask 대신 코루틴/Thread 남용 등 명백한 것만. 사소한 스타일 지적은 하지 않는다.

## 4. 다른 작업과의 교차 확인

병렬 작업 간 충돌은 단독 PR만 봐서는 잡히지 않는다. 이 프로젝트의 설계 결정은 상당 부분 이슈에 기록되므로 반드시 대조한다.

1. **접점 이슈 자동 매핑**: 이 PR이 어떤 열린 이슈들과 접점이 있는지 코드에서 역으로 추론해 리포트에 목록으로 제시한다 (충돌이 없어도 접점 자체가 리뷰어에게 유용한 정보다).
   - 접점 후보 추출 재료: ① 변경 파일의 폴더/시스템 이름 (`Round/`, `NPC/`, `Interaction/` 등) ② 변경된 클래스·이벤트·public 멤버 이름 ③ 변경 코드의 주석에 인용된 이슈 번호(#NN) — **이건 무조건 접점** ④ PR 제목·본문의 이슈 참조(`closes #N` 등)
   - `gh issue list --state open --limit 50 --json number,title`로 제목을 훑어 위 재료와 매칭되는 이슈를 고르고, 매칭된 것만 `gh issue view <n>`로 본문을 읽는다. 토큰 절약을 위해 **본문은 최대 5개까지만** 읽되, 접점 목록 자체는 제목 매칭만으로도 전부 기재한다.
   - 각 접점 이슈에 대해 본다: 이 PR의 결정이 그 이슈가 전제하는 것과 충돌하는가 — 다른 이슈가 사용/구독하기로 한 API·이벤트를 바꾸거나 제거, 이슈에 계획된 작업을 다른 방식으로 선점, 계획된 확장을 막는 구조 등. 충돌이 아니면 "접점 있음 — 문제 없음"으로만 기재.
2. **연결 이슈 요구사항 충족 확인**: PR이 해결한다고 선언한 이슈(`closes #N` 또는 제목의 이슈 번호)의 본문을 읽고, 거기 적힌 요구사항·체크리스트와 실제 구현을 대조한다. **하기로 한 것 중 빠진 항목**이 있으면 지적한다. 단, PR 본문이나 코드 주석에 "후속으로 미룸"이 명시된 항목은 지적 대신 "후속 확인"으로 분류.
3. **열린 다른 PR과 파일 겹침**: `gh pr list --state open --json number,title,files`로 이 PR과 같은 파일을 건드리는 다른 열린 PR을 찾는다 (파일 **목록만** 대조 — 내용은 읽지 않는다).
   - 겹치는 파일이 있으면 경고하고, 특히 같은 `.unity` 씬을 두 PR이 동시에 수정 중이면 **강한 경고** — Unity 씬은 사실상 머지가 불가능해, 나중에 머지되는 쪽이 먼저 머지된 쪽의 씬 작업을 덮어쓸 위험이 크다 (PR #86에서 #74의 씬 오브젝트가 삭제된 실사례 있음). 이 경우 머지 순서 조율을 권고한다.

## 5. 리포트 출력

아래 형식으로 출력한다. **문제가 없는 항목도 "확인함"으로 표기**해서 리뷰어가 무엇이 검사됐는지 알 수 있게 한다.

**심각도 등급** — 모든 지적에 하나를 부여하고, 결론에서 개수를 집계한다:
- 🔴 머지 차단 — 컴파일 깨짐, 명백한 버그, 다른 작업 파괴
- 🟠 머지 전(또는 직후) 확인·합의 필요
- 🟡 후속 조치 권장 — 별도 이슈감
- 🔵 참고 — 알아두면 좋음

🔴/🟠 지적은 **근거(파일:라인·GDD 섹션) → 시나리오(어떤 상황에서 어떻게 문제가 되는지) → 제안(다음 행동)** 3단으로 쓴다. 🟡/🔵는 근거만으로 충분.

```
## PR #<n> 자동 리뷰: <제목>

### 구현 요약
(이 PR이 무엇을 어떻게 구현했는지 2~3문장 — 리뷰어의 이해를 먼저 보여줘, 사람이 리뷰가 헛다리를 짚었는지 바로 판별하게 한다. 연결 이슈가 있으면 완료 기준을 항목별로 대조: 충족 / 부분 충족 / 미충족 / 미검증)

**결론:** 🔴 n · 🟠 n · 🟡 n · 🔵 n — 머지 가능 / 조건부 머지 가능(조건 명시) / 머지 불가 (한 줄 사유)

### 컴파일
(에러 목록 또는 "에러 없음" / "Unity 미연결로 정적 검사만 수행")

### GDD 정합성
(불일치 항목: 파일:라인 ↔ GDD 섹션, 없으면 "대조한 섹션: X장, Y장 — 불일치 없음")

### 컨벤션 / Netcode
(위반 항목 또는 "이상 없음")

### 접점 이슈 & 다른 작업과의 충돌
(이 PR과 접점이 있는 열린 이슈 목록 — 각각 한 줄 사유와 함께: "#43 본부 결과 UI — 이 PR의 OnRoundEnded를 구독할 예정, 충돌 없음". 충돌·경고가 있으면 근거와 함께 최상단에. 사람 간 조율이 필요한 항목은 **"다음 통합 지점: <이 PR 작성자> ↔ <해당 이슈/PR 담당자> — 합의할 내용"** 형식으로 명시. 접점이 하나도 없으면 "접점 이슈 없음")

### 리뷰 제외된 파일 (Editor에서 확인 필요)
(변경된 씬/프리팹/애니메이션/에셋 파일 경로 목록 — 내용 미검토. 씬/프리팹에서 삭제된 오브젝트가 있으면 "삭제됨: <이름> — 의도 확인 필요"를 함께 기재. 없으면 생략)

### 잘한 점
(눈에 띄는 좋은 설계 결정이 실제로 있을 때만 1~2개. 억지로 채우지 않는다 — 없으면 섹션 생략)

### 기타 소견
(선택 — 버그 의심, 구조 제안 등. 없으면 생략)

리뷰 기준 커밋: <PR head 커밋 SHA 7자리>
```

- 각 지적에는 근거(파일:라인, GDD 섹션 번호)를 반드시 붙인다. 추측성 지적은 "확인 필요"로 명시.
- **검증하지 못한 것을 "충족/정상"으로 단정하지 않는다.** 리뷰가 직접 확인할 수 없는 것(프리팹·씬 배선, Editor 설정값, 런타임 동작)은 완료 기준 대조와 결론에서 **"미검증 — Editor에서 확인 필요"**로 분류한다. 예: 코드가 기능을 지원해도 에셋 연결 여부를 못 봤으면 "충족"이 아니라 "부분 충족(코드 준비됨, 배선 미검증)"이다.
- `--comment` 플래그가 있으면: 리포트를 사용자에게 먼저 보여주고 **게시해도 되는지 확인받은 뒤** `gh pr comment <n> --body-file <임시파일>`로 게시한다. 임시 파일은 스크래치패드에 만든다.
